# 混色算法说明

本文说明三个混色引擎分别是什么、依据在哪里、为什么默认是现在这一个，以及怎样验证。

---

## 0. 结论先讲

- **Bambu 混色预览**（默认）：Bambu Studio **2.8**（`v02.08.02.61`）「添加混色耗材」对话框用的
  **filament_mixer 四次颜料混色多项式**（330 项特征、7 个输入，近似 Mixbox 行为）。
  实测能把用户两张截图里的**效果预览色块逐字节复现**（见 §1）。
- **Bambu 2.5 旧版预览（sRGB 平均）**：`mixed = Σ weight_i × rgb_i`，直接在 8 位 sRGB 上
  加权平均再截断。这是 **2.5.x 及更早**版本的算法，保留给仍在用旧版 Studio 的用户。
- **光谱 KM 模型**：sRGB → 线性 RGB → XYZ(D65) → Bradford 适配到 D50 → 20 项多项式 → 31 段反射率
  → K/S → 按比例混合 K/S → 反射率 → XYZ → Lab → sRGB。物理上最接近真实颜料，但与 Studio 对不上。
- 三个引擎都实现了，界面上可切换，默认用第一个，因为你的最终目的是**去 Bambu Studio 里把配方填进去**，
  那里显示什么颜色，就应该以什么颜色为准。

---

## 1. 为什么默认引擎从「sRGB 平均」换成了「颜料多项式」

最初（对着 Bambu Studio **2.5.3** 的源码）确认的结论是：对话框做的是 8 位 sRGB 加权平均。
这个结论对 2.5.3 是对的，但**对本机装的 02.08.02.61 已经过时**。

### 1.1 反算：渐变条拟合说 sRGB 平均最好

先把两张截图里 `比例` 渐变条上的采样点，用 6 种候选模型做最小二乘拟合（`tools/fit_mix_model.py`，
父色自由拟合）：

| 模型 | 截图 1 的 RMS | 截图 2 的 RMS |
| --- | --- | --- |
| sRGB 加权平均 | 14.55 | 12.96 |
| 线性光空间加权平均 | 37.36 | 31.47 |
| gamma 2.0 加权平均 | 35.56 | 28.91 |
| Lab 插值 | 68.67 | 67.82 |
| K/S 混合 | 68.67 | 67.82 |

sRGB 平均胜出——但**残留 RMS 有 13～15，不是 0**，说明「拟合得最好的那个」并不等于「就是它」。

### 1.2 读源码：02.08 的对话框换了算法

直接取 Bambu Studio `v02.08.02.61` 的源码，对话框已经**不再是加权平均**：

```cpp
// src/slic3r/GUI/MixedFilamentDialog.cpp  @ v02.08.02.61
static wxColour blend_colors(const wxColour& a, const wxColour& b, double ratio_a)
{
    unsigned char r, g, bl;
    Slic3r::filament_mixer_lerp(a.Red(), a.Green(), a.Blue(),
                                b.Red(), b.Green(), b.Blue(),
                                static_cast<float>(1.0 - ratio_a), &r, &g, &bl);
    return wxColour(r, g, bl);
}
```

`blend_n_colors()` 也改成拼十六进制颜色串 + 整数权重后调用 `Slic3r::blend_color_multi()`。
该文件在 02.08 新增了 `#include "libslic3r/FilamentMixer.hpp"`——2.5.3 里没有这个 include。

调用点：`效果预览` 色块、`比例` 渐变条、`混色推荐` 的两色/三色候选块，全部走这个函数。

### 1.3 定论：逐字节复现两张截图

把 `#FFFFFF` + `#000000` 喂给颜料多项式，和截图上量出来的预览色块对照：

| 截图 | 截图里量到的预览色 | **颜料多项式** | 旧版 sRGB 平均 |
| --- | --- | --- | --- |
| 截图 1（1 @ 90% + 2 @ 10%） | `#CBE4EE` | **`#CBE4EE` ✅ 完全一致** | `#E5E5E5`（R/G 差 26/27） |
| 截图 2（1 @ 10% + 2 @ 90%） | `#041D2E` | **`#041D2E` ✅ 完全一致** | `#191919`（R 差 21） |

两个色块都是**逐字节相同**。这比渐变条拟合强得多：拟合是在「父色未知、采样位置未知」的情况下
猜参数，而这里是「父色已知（纯白 + 纯黑）、结果已知」，多项式直接命中。
旧版 sRGB 平均在这两处分别差了最多 27 和 21 个色阶，不可能同时对上。

**这条不变量已经锁进测试**：`tests/test_engine.py::FilamentMixerEngineTests::test_it_reproduces_the_reference_screenshots_byte_for_byte`。

### 1.4 界面细节（从源码确认）

- `比例` 渐变条是**整条 0%→100%** 的扫描（`double t = (double)x / sz.GetWidth();`
  `blend_colors(col_a, col_b, 1.0 - t)`），左端是第一种耗材的纯色，右端是第二种，
  白色分隔线画在第二种耗材的百分比处——所以截图 1 的分隔线靠左、截图 2 靠右。
- 两色比例被夹在 10%–90%（`std::max(10, std::min(90, new_ratio))`），`MAX_COMPONENTS = 3`。
- 推荐色块用 `0.5/0.5`（两色）与 `0.25/0.25/0.50`（三色）。
- **只允许同种「耗材种类」混色**：类型不匹配时确认按钮直接禁用，并弹出红字提示。

## 2. 颜料多项式（默认引擎）的完整实现

引擎实现：`app/core/engines.py::FilamentMixerEngine`，
算法：`app/spectral/filament_mixer.py`，系数表：`app/spectral/filament_mixer_profile.py`。

1. **输入 7 个数**：`x = [r1, g1, b1, r2, g2, b2, t]`，颜色是 **0–255**，`t` 是**第二种**耗材的占比
   （对话框传的是 `1.0 - ratio_a`）。注意这里**没有**任何 sRGB↔线性转换，多项式直接在 0–255 上算。
2. **短路**：`t ≤ 0` 直接返回颜色 1，`t ≥ 1` 直接返回颜色 2，**不评估多项式**。
   所以 100/0 与 0/100 是精确还原原色的（这也是端点测试能断言相等的原因）。
3. **330 项特征**：`features[i] = Π_j x[j]^POWERS[i][j]`，指数来自 `POWERS[330][7]`，
   每行指数 0–4 且行和为四次。
4. **每通道线性求和**：`sum_c = INTERCEPT[c] + Σ_i features[i] × COEF[i][c]`。
5. **截断取整**：`int val = static_cast<int>(sum)` 后夹到 0–255。
   这是**截断不是四舍五入**，NumPy 侧用 `np.clip(raw, 0, 255).astype(np.int64)` 对应。
   （注意 `FilamentMixer.cpp` 里另一个辅助函数 `to_u8()` 是 `+0.5f` **四舍五入**的，
   对话框的预览路径不走它，别混用。）
6. **三色及以上**：`blend_color_multi()` 会**先**查 Bambu 私有的实测混色表
   `lookup_measured_blend_color()`，查不到才按顺序两两复合、每步量化到 8 位。
   本程序只有两个颜色，走的就是多项式这一条。

**系数的来源与自检**：`tools/gen_filament_mixer_profile.py` 解析上游头文件
`tools/reference/FilamentMixerModel.hpp`，校验每行指数后写出 `filament_mixer_profile.py`；
生成前会用上游文档给出的样例 `lerp(0,33,133, 252,211,0, 0.5) == (47,141,56)`
做自检，**不通过就拒绝写文件**。随时可以用 `--check` 复核现有系数表是否与头文件一致。

> 蓝 + 黄 → 绿：颜料模型给 `#2F8D38`，朴素 RGB 插值给 `#7E7A43`。
> 这正是「颜料混合」和「光的混合」的根本区别，也是这个模型存在的意义。

**验证数据**（`tests/test_engine.py::FilamentMixerEngineTests`）：

| 输入 | 输出 |
| --- | --- |
| `lerp(0,33,133, 252,211,0, 0.5)` | `(47, 141, 56)` —— 上游文档样例 |
| `#FFFFFF` + `#000000` @ 90/10 | `#CBE4EE` —— **与截图逐字节一致** |
| `#FFFFFF` + `#000000` @ 50/50 | `#637E9F` |
| `#FFFFFF` + `#000000` @ 10/90 | `#041D2E` —— **与截图逐字节一致** |
| `#3D7BC8` + `#FF8800` @ 100/0 | `#3D7BC8`（短路，精确） |

**两个必须知道的性质**：

- 它有**真实的偏蓝倾向**：纯白 + 纯黑在 90/10 时是 `#CBE4EE` 而不是灰——蓝通道比红通道高 35。
  这不是 bug，而是模型的固有行为（也正因为如此，sRGB 平均永远拟合不上那两张截图）。
- 它是**回归拟合，不是恒等变换**：把颜色和它自己混（`lerp(c, c, t)`）会有漂移。
  在最差的纯蓝上，整个 10%–90% 扫描里最大漂移是 **21 个色阶**（`#FF00FF` 20、`#FF0000` 与
  `#00FF00` 13）；只看 50/50 的话最大是 8，容易低估，所以 `tools/probe_engine.py` 的 0c 段
  是**按全部 81 个比例**扫的。**不要**把「对称性」或「自混不变」写成断言等号；
  测试里断言的是上界（`tests/test_engine.py::test_a_self_mix_is_close_to_the_input`，上界 24）。

## 3. 旧版引擎：Bambu Studio 2.5 的 sRGB 加权平均

```cpp
// src/slic3r/GUI/MixedFilamentDialog.cpp  @ v02.05.03.62
static wxColour blend_colors(const wxColour& a, const wxColour& b, double ratio_a)
{
    double rb = 1.0 - ratio_a;
    return wxColour(
        (unsigned char)(a.Red()   * ratio_a + b.Red()   * rb),
        (unsigned char)(a.Green() * ratio_a + b.Green() * rb),
        (unsigned char)(a.Blue()  * ratio_a + b.Blue()  * rb));
}
```

要点：均值取在**伽马编码后**的 8 位值上（所以在 sRGB 空间是直线，在线性光空间不是），
并且 `unsigned char` 转换是**截断**。该版本的对话框里没有出现任何 `spectrum` / `ks` /
`kubelka` 字样，也没有 `FilamentMixer` 的 include。

**验证数据**（`tests/test_engine.py::BambuEngineTests`）：

| 输入 | 输出 |
| --- | --- |
| `#FFFFFF` + `#000000` @ 90/10 | `#E5E5E5` |
| `#FFFFFF` + `#000000` @ 50/50 | `#7F7F7F` |
| `#FF0000` + `#FFFF00` @ 50/50 | `#FF7F00` |
| `#000000` + `#010101` @ 50/50 | `#000000`（证明是截断不是四舍五入） |
| `#3D7BC8` + `#FF8800` @ 30/70 | `#C4843C`，且 70/30 结果相同（对称） |

## 4. 光谱 KM 模型的完整链路

引擎实现：`app/spectral/color.py`，系数表：`app/spectral/icc_profile.py`。

1. **sRGB → 线性**：`v ≤ 0.04045 ? v/12.92 : ((v+0.055)/1.055)^2.4`
2. **线性 RGB → XYZ(D65)**：标准 sRGB 矩阵
   ```
   [0.4124564 0.3575761 0.1804375]
   [0.2126729 0.7151522 0.0721750]
   [0.0193339 0.1191920 0.9503041]
   ```
3. **Bradford D65 → D50**，再 ×100（ICC 多项式要求在 D50 下）
4. **20 项多项式**，顺序固定：
   `1, X, Y, Z, X², Y², Z², XY, XZ, YZ, X³, Y³, Z³, X²Y, X²Z, XY², XZ², Y²Z, YZ², XYZ`
5. **反射率**：`reflectance[w] = Σ_term C[w][term] × term`，31 个波长（400–700 nm，步长 10 nm）
   - 注意：估计值**不保证落在 [0,1]**（实测白色 min 0.3979 / max 1.0309，黑色 min −0.0079 / max 0.0246）。
     这是 ICC 这个多项式估计器的固有性质，不是 bug。
6. **反射率 → K/S**：`ks = (1−r)² / (2r)`，其中 `r = clamp(r, 0.001, 0.999)`
   ——**这一步的 clamp 就是光谱引擎在 100/0 时不能完全还原原色的原因**（最大 ΔE00 ≈ 20.5）。
7. **混合**：`ks_mix[w] = Σ weight_i × ks_i[w]`，权重按百分比归一化。
8. **K/S → 反射率**：`r = clamp01(1 + f − √(f² + 2f))`，`f = max(0, ks)`
9. **反射率 → XYZ → Lab**：CIE 1931 **10°** 观察者 + **D65** 光源，
   白点用同一组常数 `(94.811, 100.0, 107.304)`，枢轴 `δ = 6/29`。
   > 这一条很关键：`lab_from_rgb` 和 `lab_to_rgb` 必须用**同一个白点**。
   > 早期版本一个用 2° D65、一个用 10° D65，往返误差高达 17 个 sRGB 灰阶，已修正。
10. **Lab → sRGB**：白点 `(94.811, 100.0, 107.304)`，逆枢轴，标准 sRGB 逆矩阵，
    `linear_to_srgb(v) = v ≤ 0.0031308 ? 12.92v : 1.055v^(1/2.4) − 0.055`，clamp01，四舍五入。

**与上游的差异**（有意为之）：

- 没有使用 `FullSpectrumKSPairResidual` 的成对残余修正，也没有 `MaterialHigherOrderProfile`
  的三阶/四阶残余——这些只在**材料能从数据库中识别出来**时才生效（`material_index` 有值）。
  用户录入的是任意 RGB，`material_index = nullopt`，上游在这种情况下同样会跳过全部残余项，
  只走「估计锚点光谱 + 纯 K/S 混合」这一条通用路径。
- 没有乘 `optical_strength`，因为本程序不采集 `td_mm`（单层光学厚度）参数。

## 5. 三个引擎的实测差异

以 `#FFFFFF` + `#000000` 为例（L\* 由 `app/spectral/color.py::lab_from_rgb` 直接算出，
即「这个 sRGB 十六进制对应的 L\*」，不是走光谱估计那条路）：

| 白色占比 | 颜料多项式（默认） | 旧版 sRGB 平均 | 光谱 KM |
| --- | --- | --- | --- |
| 10% | `#041D2E`，L\* 9.8 | `#191919`，L\* 8.8 | `#0C0C04`，L\* 3.2 |
| 50% | `#637E9F`，L\* 51.9 | `#7F7F7F`，L\* 53.2 | `#121308`，L\* 5.5 |
| 90% | `#CBE4EE`，L\* 89.1 | `#E5E5E5`，L\* 90.9 | `#2E301C`，L\* 19.1 |

数字可由 `tools/probe_engine.py` 的 0e 段现场复算。

光谱模型给出的黑白混合**远暗于**另外两个——这在物理上是对的方向（颜料混合是减色的，
白+黑不会得到中灰），但和 Bambu Studio 对话框里显示的颜色完全对不上。
颜料多项式与 sRGB 平均在中灰附近接近，但在两端差别很大（这正是「偏蓝」的来源）。

## 7. 已知的验证缺口

- **实测混色表无法复现**：`blend_color_multi()` 会先查 Bambu 私有的
  `lookup_measured_blend_color()`，那是随 Studio 分发的实测数据，第三方拿不到。
  本程序走的是「查不到 → 多项式」这条分支，对**用户自己录入的任意 RGB** 而言，
  这正是 Studio 也会走的那条路。
- 渐变条拟合的残留 RMS 仍有 3～6：那是截图管线的**色调曲线**造成的
  （截图里黑端量到的是 `#00070F` 而不是纯黑），不是模型曲率。
  逐字节复现预览色块这一条比拟合更具决定性。
- 用户的两张截图是**纯白 + 纯黑**这一组。其他颜色组合没有权威数值对可对，
  所以其余部分的验证是**源码保真 + 内部不变量**（上游样例、短路端点、单调性、自混上界）。
- 上游 `FilamentMixerModel.hpp` 声明 Mean ΔE ≈ 2.07；本程序只保证**转录逐位一致**，
  不保证该模型本身对真实打印的精度。

## 8. 启动可靠性：数据目录、写入探测与 `mkstemp` 陷阱

这不是混色算法，但它和引擎一样属于「实测出来的结论」，而且它的现象最容易被误判。

**现象**：用户报告「程序必须管理员权限才能打开」。双击没反应；以管理员身份运行就正常。

**先排除的四件事**（都实测过，都不是原因）：

| 怀疑对象 | 实测结果 |
| --- | --- |
| exe 清单要求提权 | `requestedExecutionLevel level="asInvoker" uiAccess="false"`，根本不请求提权 |
| 兼容性标记强制以管理员运行 | `HKCU\...\AppCompatFlags\Layers` 与 `HKLM\...\Compatibility Assistant\Store` 里都没有本程序的条目 |
| SmartScreen / 网络下载标记 | 没有 `Zone.Identifier` 数据流，文件属性只有 `Archive` |
| 目录 ACL 拒绝 | `%LOCALAPPDATA%\BambuPalette` 的 ACL 与 `%LOCALAPPDATA%` 完全一致，`SYSTEM` / `Administrators` / 当前用户都是 `FullControl` |

**真正的复现方式**：不要用自己的 shell 启动（那是高完整性级别，能写进用户配置目录，永远复现不出来），
而是用 `Start-Process explorer.exe -ArgumentList "<exe>"` —— 由资源管理器拉起，子进程拿到的就是普通双击时的令牌。
这样启动后：进程存在、22 个线程、**没有任何主窗口**，CPU 在 44 秒里烧掉 42.2 秒（≈97%）。

**抓到现场**：`py-spy dump --pid <pid> --locals` 给出的调用栈是

```
_mkstemp_inner (tempfile.py:263)  ←  mkstemp (tempfile.py:357)  ←  save (app\core\library.py:278)
  ←  _save_library (main_window.py:354)  ←  _reload_library (main_window.py:350)
  ←  __init__ (main_window.py:76)  ←  main (app\main.py:75)  ←  <module> (launcher.py:16)
```

局部变量把答案摊开了：`dir = C:\Users\xzz\AppData\Local\BambuPalette`，`seq = 1025160` —— 一百多万次失败重试。
`tempfile.py:263` 位于 `except PermissionError:` 分支内部，所以抛的确实是 `PermissionError`（拒绝访问）。

**机制**（CPython 3.12 `Lib/tempfile.py:243-271`，逐行读过）：

```python
for seq in range(TMP_MAX):                 # TMP_MAX = 2147483647
    ...
    try:
        fd = _os.open(file, flags, 0o600)
    except FileExistsError:
        continue
    except PermissionError:
        if _os.name == 'nt' and _os.path.isdir(dir) and _os.access(dir, _os.W_OK):
            continue                       # ← 把"拒绝写入"误判成"文件名撞车"，然后继续重试
        raise
```

`os.access(dir, os.W_OK)` 只看 DACL。**强制完整性标签（mandatory integrity label）不在 DACL 里**，
"delete pending"、杀毒软件锁同理。于是只要「目录存在 + 看起来可写 + 实际持续拒绝创建」，
`mkstemp` 就从"原子保存"变成一个跑满单核两亿多次的死循环。又因为
`_reload_library()` 在 `MainWindow.__init__` 里无条件存了一次档，窗口还没显示就先卡死——
用户看到的就是"程序打不开"，而管理员能开只是因为高完整性进程确实写得进去。

**为什么之前的验收全是绿的**：`app/selftest.py` 会把 `paths.library_path` 和 `paths.data_dir`
monkeypatch 到一个私有临时目录，所以 `--selftest` 从来没有碰过真实数据目录。

**修复**（四处，都在 `app/`）：

- `app/core/paths.py::_write_probe()` —— 判断目录能不能用**不再看存在性**，而是真的
  `open(probe, "x")` 建一个文件再删掉。`open` 不会重试，一次拒绝就是一次拒绝。
  `data_dir()` 的候选顺序变成：接管旧目录 → `mkdir` → `is_dir()` → 写入探测 → 播种档案，
  任一步失败就记下中文原因并继续下一个候选。
- `app/core/paths.py::_candidate_roots()` —— 兜底链多了一级 **exe 旁边的 `data\`**，
  且只在 `is_frozen()` 时加入（从源码运行不会往工程目录里写东西）。
  （1.6.11 把这一级从"最后才轮到"提到**首选**，profile 反过来变成带副本名的退路——见 §37.9。）
- `app/core/library.py::_write_temp_file()` —— 保存改用**有上限**的 `open(..., "x")` 循环
  （`<档案名>.<pid>.<n>.tmp`，最多 8 次）：`FileExistsError` 才继续，其他 `OSError`
  立刻变成可读的 `LibraryError`。文件仍然先写临时文件再 `os.replace`，原子性不变。
- `app/core/paths.py::scratch_dir()` —— `tempfile.mkdtemp` 有同样的无界重试，自检改用有界 `mkdir` 循环。

**顺带修掉的第二个坑**：`data_dir()` 现在**优先选已经有档案的目录**（多份都有则选最新的）。
否则会这样丢数据：程序曾在低完整性级别下把档案写到 exe 旁边，之后首选目录恢复可写，
程序就切回去读一个空档案，用户看到耗材"凭空消失"。便携模式（`portable.txt`）例外——
那是用户的明确意图，必须压过这条启发式。

**验证**：单元测试 160 → 179 条（`WriteProbeTests` / `UnwritableRootTests` / `SteadyStateRootTests` /
`ScratchDirTests` / `LibrarySaveTests`）；同一个 exe 用 `explorer.exe` 拉起后
**主窗口出现、标题为 `BambuPalette — 混色耗材色彩管理器`、6 秒内 CPU 增量为 0**，
数据落在 exe 旁边的 `data\`（因为该机器上用户配置目录对普通完整性进程确实不可写）。
从源码（高完整性）运行时 `paths.data_dir()` 仍然返回 `%LOCALAPPDATA%\BambuPalette`，
说明兜底只在真正需要时才启用。

## 9. 3MF 导出的验证（已实测，非推测）

本机装有 **Bambu Studio 02.08.02.61**（`C:\Program Files\Bambu Studio\bambu-studio.exe`），
所以 3MF 走了真实的往返验证：


原理：Bambu Studio 继承自 PrusaSlicer，支持 `--export-3mf <输出> <输入>`——它会**读入**给定文件、

`tools/verify_bambu_roundtrip.py` 就是这么做的，并且会在「回读得到 0 个三角面」「三角面少于源文件一半」
「一个 `<part>` 都没保住」时直接判失败、退出码非 0。

**实测（`samples/sample-plate.3mf`）**：

| | 字节 | 顶点 | 三角面 | 网格 | 部件 |
| --- | --- | --- | --- | --- | --- |
| 源文件 | 62,589 | 3,076 | 9,164 | 6 | 6 |
| Bambu 回读 | 100,892 | 3,076 | 9,164 | 6 | 6 |

六个部件的名称与挤出机号（1 / 1 / 2 / 3 / 4 / 5）逐条一致。

### 这一步抓到的真实缺陷

第一版 3MF 是照抄 Bambu Studio 自己导出工程的布局：

- `3D/3dmodel.model` 只放一个组装对象，用 `<component p:path="/3D/Objects/object_N.model" objectid="1" …>`
  跨文件引用部件几何；
- 根节点带 `requiredextensions="p"`，以及 production 扩展要求的 `p:UUID`。

看起来最「保真」，但把这份文件交给真的 Bambu Studio 之后，它**保留了全部元数据、却把每一个 component 都丢掉了**：

```
3D/3dmodel.model        <object id="1" …><components>\n</components></object>   ← 空的
3D/Objects/object_1.model   <resources>\n</resources>                            ← 空的
model_settings.config   <metadata face_count="0"/>                             ← 没有面
```

也就是说模型导进去了，但**几何是空的**。单元测试当时全绿——因为它检查的是「条目的存在与否」，
而不是「Bambu 能不能解出几何」。

改成**标准 core 3MF** 之后往返完全一致：

- 所有部件的 `<mesh>` 内联在同一个 `3D/3dmodel.model` 里，编号 1…N；
- 组装对象编号 N+1，`<components>` 只按 `objectid="1"…"N"` 引用，不再有 `p:path`、不再有 `requiredextensions`；
- 每个部件的 id 与 `Metadata/model_settings.config` 里 `<part id="…" extruder="…">` 的 id 一一对应，
  这正是承载挤出机分配的地方。

回归测试锁在 `tests/test_export.py`：

- `test_meshes_are_inline_rather_than_spread_over_part_files` —— 不许出现 `3D/Objects/` 条目、
  不许出现 `requiredextensions`，且 `<mesh>` 数量必须等于部件数；
- `test_every_component_resolves_to_an_inline_object` —— 每个 `<component>` 的 `objectid`
  都必须能解析到一个真正带 `<mesh>` 的对象（就是 Bambu 卡住的那条不变量）。

## 10. 把颜色写进模型里：`<basematerials>` + `paint_color`

第一版 3MF 是「一个颜色一个部件」，颜色只存在于 `Metadata/model_settings.config` 的挤出机号里。
拿到真机上试，结果是**整块底板变成 AMS 里那个耗材的颜色**——因为模型本身不带颜色，
Bambu Studio 只能拿「分给这个部件的 AMS 槽位」去涂。

参考已有的真·多色工程 `2-有ams_多色版.3mf` 之后确认，Bambu Studio 的多色是**逐三角面**编码的：

- `3D/Objects/object_14.model` 里 `basematerials="0"`、`pid="0"`，但每个 `<triangle>` 带
  `paint_color="…"`，例如 `<triangle v1="0" v2="1" v3="2" paint_color="4"/>`；
- 全文只有 3 个不同的取值（`4` ×15464、`0C` ×418、`1C` ×320），正好对应它的
  `filament_colour = ["#FFFFFF", "#FF8000", "#000000", "#FFFF00"]` 里的第 1、3、4 号。

码表在 BambuStudio 源码 `src/libslic3r/Model.cpp` 的 `CONST_FILAMENTS`（第 57–60 行）：

```
"", "4", "8", "0C", "1C", "2C", "3C", "4C", "5C", "6C", "7C", "8C",
"9C", "AC", "BC", "CC", "DC", "EC", "0FC", "1FC", … "EFC"
```

**一个三角面整块属于某一种耗材时，直接写这一串就完了**（不需要做位运算）：
1 号 → `4`、2 号 → `8`、3 号 → `0C`、4 号 → `1C` …… 超过 32 种耗材时
`get_real_filament_id` 会返回空串（`Model.cpp:4119`）。

于是 `app/mesh/threemf.py` 现在两个都不落下：

- 文档里放 `<basematerials id="99">`，每一项是 `<base name="白" displaycolor="#FCF4F0FF"/>`；
- 每个三角面同时写 `pid="99" p1="挤出机号-1" paint_color="码表值"`，两种编码必然一致（可用
  `samples/sample-plate.3mf` 交叉验证：`p1` 计数与 `paint` 计数逐项相等）。

同时底板是**一整块**：所有颜色的方块合并进**同一个** `<mesh>`，颜色靠逐面色区分，
而不是拆成「底板 + 每种颜色一个部件」——后者在 Bambu Studio 的对象列表里会列出一长串部件。

## 11. 图片转模型：为什么会出现「麻点」以及怎么修

用户的图片 `samples/user-pig.png` 是一张 1024×1024 的 AI 插画，猪身上有一层 ±3 的纸张纹理
（一个 100×100 的小块里就有 1,994 种不同的颜色）。原来的流程：

1. `reduce_colours` 按颜色预算把这张图量化；
2. 纹理被拆成了**两个**几乎一样的色心（差不到 1 个 ΔE00）；
3. 这两个色心各自去库里找最近的混色，**分别**匹配到了 `#F6D9D6`（粉）和 `#F5E1AE`（奶黄）——
   这两个颜色**互相**差了 6 个以上的 ΔE00；
4. 于是图片自己的噪声决定每个像素归谁，整块平面被切成粉/奶黄的细密条纹。

实测：512×512 的匹配出 8 种颜色，其中三对互相的 ΔE00 只有 **1.66 / 1.74 / 1.53**；
沿第 256 行有 **107 次**颜色索引跳变。后果不只是难看——每一对「看起来一模一样」的颜色
都要占一个 AMS 槽位，用户白白多换好几次料。

修法是 `MatchSettings.merge_delta_e`（默认 **2.0**）配上两次并查集合并：

- `_merge_similar_colours`：合并**量化后的色心**，保留像素最多的那个色；
- `_merge_indistinguishable`：合并**匹配结果**，同样保留用得最多的那个，
  再按像素数从多到少重新编号。

修完同样条件下：颜色数 **8 → 4**，沿该行的索引跳变 **107 → 7**，
底板部件 **9 → 5**。`tests/test_image.py` 里有一条对照测试：
把 `merge_delta_e` 设成 0，同一个人造噪声平面立刻重新「花」起来——
这证明是合并起的作用，而不是那张图本来就简单。

## 12. 「图片里的颜色」为什么不是匹配色的 RGB

右侧面板要同时显示两个颜色，所以匹配结果必须**分别**记住两件事：

- `MatchResult.palette[i]` —— 库里那个**能打出来**的颜色（耗材本色或混色），
  右边显示的是它，配方也是它；
- `MatchResult.means[i]` —— 图上这块区域**自己**的平均 sRGB，
  在重编号之后用 `np.add.at(totals, flat[valid], pixels[valid])` 按区域累加再除以像素数得到。

左边卡片显示 `means[i]`，右边卡片显示 `palette[i]`，两者之间的 CIEDE2000 色差就是
面板上那个 ΔE00。想看「差了 10 个 ΔE00 还挺多」的实时反馈，靠的就是这个分离——
如果两边都拿 `palette[i]` 显示，这个数字永远是 0，面板也就没有意义了。

## 13. 导入 41 卷耗材后「图片只认出两个颜色」

用户导入大简 PETG HF 的 41 卷色卡后，同一张猪的插画被判成**两种**颜色
（`#FAD4B8` 98.3 % + `#46352B` 1.7 %），眼睛是浅灰的。这里其实是**三个**独立的缺陷叠在一起。

### 13.1 索引溢出：66,461 个颜色装不进 `int16`

41 卷耗材 = 41 + C(41,2)×81 = **66,461** 个调色板条目。而每个像素的分类图原来是 `int16`：

```python
remap = np.full(..., dtype=np.int16)     # 改之前
```

`int16` 最大 32,767。`_nearest_entries` 返回的下标一旦超过这个数就**回绕成负数**，
而负数在下游到处都是「透明、没有匹配」的意思，于是那些颜色被静默删掉。
实测：`chosen = [23, 41590, 43315, 13602, 1]`（5 种颜色）→ `used = [1, 23]`（只剩 2 种）。

修法是让 dtype 跟着**调色板**的大小走，而不是跟着「这张图会用几种颜色」走：

```python
_INDEX_DTYPE = np.int32
```

`tests/test_image.py` 的 `LargePaletteTests` 用 30 卷耗材凑出 35,265 个条目复现这条路径，
断言每个色带都还有像素、没有任何下标为负。

### 13.2 透明背景被当成黑色

`image.convert("RGB")` 会把透明像素变成**纯黑**。猪这张图透明背景占 262,144 像素里的
**138,095**，于是中位切分把大半预算花在黑色和它边缘的抗锯齿上，真正的颜色反而挤没了。

现在 `reduce_colours(image, settings, mask=None)` 接收透明度掩码：先把不透明像素**压实**成
一条一行的色带再去量化，量化完把类别**散回**原图，掩码外面一律标 `-1`。
压实后的色带没有「相邻像素」这回事，所以这条路径上强制关掉误差扩散
（`FLOYDSTEINBERG` 只会撒噪声）；`keep is None` 时仍然照旧支持抖动。

配套的三处也要跟着改：

- `_smooth_colours` 用的是**带掩码的**均值滤波（`sum(rgb*mask)/sum(mask)`），
  否则透明区域会渗进来把边缘染黑；
- `_class_means` 取的是**原始**像素的均值，不是平滑后的——色卡和 ΔE00 才诚实；
- `_merge_similar_colours` 的 `np.bincount` 必须先滤掉 `-1`，不然它会和 0 号类挤在一起，
  保留错的那个色。

### 13.3 中位切分被大面积平色吃光预算

即使加了掩码，猪身上那层纸张纹理（±3）还是能让中位切分把 12 个槽位里的 10 个用在
「几乎一样的米色」上，眼睛（约 1,700 像素，占 0.4 %）和头发一个槽位都拿不到。

修法是**超额采样再收拢**：

```python
_OVERSAMPLE = 6
budget = min(256, max(settings.max_colours, settings.max_colours * _OVERSAMPLE))
```

先按 6 倍预算去量化，让「小而不同」的区域有机会拿到自己的色心，再收拢回用户要的数量。

收拢**不能**用并查集。并查集比较的是「和阈值内的任何一个都算一类」，
而一条**平滑渐变**上每个色心都和邻居差不到一个阈值——链条一路传下去，
金→红的渐变会整个塌成**一种**颜色（实测就是这么挂的，
`test_a_gradient_respects_the_colour_budget` 报 `1 not greater than or equal to 2`）。

所以 `_fold_clusters` 用的是**领头（leader）聚类**：

1. 按像素数从多到少走一遍色心；
2. 一个色心只有在「和**已有领头**的距离都 ≥ 阈值」且「领头还没满 `max_colours`」时才当领头；
3. 走完再把每个色心归到最近的那个领头。

关键在于色心只和**领头**比，从不和邻居比，所以渐变能留下好几个代表，
而平色的那堆近似色仍然会并到第一个领头上；按像素数排序又保证了
「小而不同」的区域排在「又一片差不多的底色」前面。

### 13.4 实测

同一张猪、同一个 41 卷色卡、`max_colours=12`：

| | 改之前 | 改之后 |
|---|---|---|
| 识别出的颜色 | 2 | **12** |
| 眼睛 | 浅灰 | `#423B36 → #3F3C38`（ΔE00 **2.39**） |
| 头发 | 并进米色 | `#774329 → #794D37`（ΔE00 3.64） |
| 最差 ΔE00 | — | 3.64（配色前是 13.42） |
| 匹配耗时 | — | 1.2 s（66,461 个条目） |

`tests/test_image.py` 里 `ClusterFoldingTests` 直接钉住「不链式合并」这条性质：
四个 L* 依次相差 1.5 的颜色（首尾差 4.5，阈值 2.0）必须折成**两**个代表，
并查集会折成一个。

## 14. 41 卷耗材下的两个卡顿 / 误解

导入 41 卷大简 PETG HF 之后（41 + C(41,2)×81 = **66,461** 个颜色）出现两个问题，
一个是真的慢，一个不是 bug。

### 14.1 「全部混色」只剩一种 —— 其实是筛选

双击某个混色（或点右侧面板的「只看这一对耗材的全部混色」）会把网格收窄成
**那一对耗材的 81 个配比**。大简的「松石绿 × 青色」81 个配比本来就都是青色系，
看起来就像「只有一种颜色」。

改之前唯一的出路是工具栏右上角的「显示全部混色」，加上网格底下一行小字，
很容易看不见。改之后：

- 网格上方多一条**筛选提示条**（`QFrame#filterBar`，浅绿底 + 绿边），
  写出筛选理由和数量：「只看 松石绿（#0AA2A4） × 青色（#047EBA） 的 81 个配比：
  现在显示 81 个，另外 66339 个没有显示。点右边的按钮可以回到全部混色。」
- 提示条自己带一个「显示全部混色」按钮；
- 工具栏的「显示全部混色」按钮同时变成强调色；
- 右侧面板那个按钮就地变成「显示全部混色」，再点一下就是从筛选里退出。

也就是说「怎么恢复」的答案在界面上有三处，不用再找。

### 14.2 「更换颜色」经常未响应 —— 一次性建了 66,461 个控件

`ColourPickerDialog` 原来是「有多少候选就建多少个 `QListWidgetItem`」，
每个 item 还要**单独渲染一张色块 pixmap**、**单独算一次 `delta_e_2000`**，
全部在 GUI 线程上跑，而且每次敲搜索框、每次换排序都重来一遍。

实测（41 卷 / 66,461 个候选）：

| | 改之前 | 改之后 |
|---|---|---|
| 打开「更换颜色」 | **26.47 s** | **0.60 s** |
| 输入一次搜索 | 27.28 s | 0.25 s |
| 五种排序各切一遍 | 134.38 s | 0.83 s |
| 打开时真正建出来的行 | 66,461 | 200（往下滚继续加） |

三处修改：

1. **相似度排序改成一次向量化 CIEDE2000**。`sort_palette` 遇到
   `SORT_SIMILARITY` 时用 `np.asarray(_color.delta_e_2000(labs, target_lab))`
   一次算完 66,461 个 ΔE00，再 `np.argsort(kind="stable")`；
   以前是逐条 Python 调用。
2. **列表按批建行**。`LIST_CHUNK = 200`，先建一批，滚到底再建下一批
   （`_extend`），窗口第一次显示后 `_fill_viewport` 最多再补 8 批，
   保证列表一定能滚动。
3. **`_rows` 是全量结果，`_shown` 是已建行数**，选中行按下标 O(1) 取，
   不再用 `UserRole` 存 key 再回头扫一遍。

搜索框还加了 200 ms 防抖（`SEARCH_DELAY_MS`），并且**一个混色的检索串
里也带上了它两个母材的品牌 / 名称 / 种类**，所以搜「大简」既能搜到耗材，
也能搜到由它混出来的混色。

**踩过的坑**：第一版 `_extend` 写成「一直加，直到滚动条能滚为止」。
控件还没布局时 `verticalScrollBar().maximum()` 恒为 0，于是这个循环
一口气把 66,461 行全建了，打开时间没有任何改善（还是 26.5 s）。
必须**一批一批加**，并把「补满视口」挪到 `showEvent` 之后。


## 15. 加一卷耗材不该等 3 秒：混色表的增量更新

### 15.1 问题

41 卷耗材 = C(41,2) × 81 = **66,420** 个混色。每个混色是一个冻结的
`MixRecipe` 对象，整表 `MixCatalog.build()` 要 **3.15 s**。

而 `MainWindow._rebuild_catalog()` 以前是**每次耗材列表一变就整表重算**：
加一卷、删一卷、改个名字，窗口都要卡 3 秒。这和 §14 的「未响应」是同一类
毛病 —— 用户只是点了一下「加耗材」，程序却在后台重算 66,420 个对象。

### 15.2 做法：`MixCatalog.sync(filaments)`

不改已经算好的部分，只补差额：

1. 先算出三个集合 ——
   - `gone`：原来有、现在没了的耗材 id；
   - `moved`：还在、但 **RGB 变了** 的耗材 id（`FilamentLibrary.update`
     是 `existing.copy(**changes)`，旧对象留在 `_by_id` 里，所以这里比得
     出颜色有没有被改）；
   - `added`：新出现的耗材。
2. `moved` 非空 → **整表重建**（改了颜色，和它相关的 80 个混色全要重算，
   增量不划算）。
3. `gone` 非空 → 只**过滤**掉含这些 id 的 `_recipes` / `_pairs` / `_by_pair`，
   然后把 id 从 `_by_id` 里删掉。**不重排 `pair_index`** —— 它只用来在
   「按母材组合」下排序和分组（`app/ui/mix_grid.py:198`、
   `app/core/image_matching.py:185`），从来不当作 `pairs` 的下标使用，
   而重排就得重建每一个冻结的 `MixRecipe`，正好是我们要省掉的开销。
   代价是删过耗材之后 `pair_index` 会有空洞，这是刻意的。
4. `added` 非空 → 只把**新出现的那些对**丢给 `_compute_pairs()`：
   `[(老的, 新的) 所有组合] + [(新的, 新的) 组合]`。

`build()` 也被拆成两半：`build()` 只负责重置状态和列出全部配对数，
真正的向量化计算搬到 `_compute_pairs(pairs)`，于是它可以被反复调用，
每次都从 `pair_index = len(self._pairs)` 接着往下编号。

### 15.3 实测（41 卷 / 66,420 混色）

| | 改之前 | 改之后 |
|---|---|---|
| 加一卷（混色表） | 3.151 s | **0.134 s** |
| 删一卷（混色表） | 3.151 s | **0.007 s** |
| 加一卷（整个窗口） | ~3.2 s | **0.166 s** |
| 删一卷（整个窗口） | ~3.2 s | **0.058 s** |

正确性用「和整表重算逐条比对 key」来兜底：`tests/test_engine.py` 里的
`test_sync_adding_a_spool_matches_a_full_rebuild` 等六个用例，以及
`tools/smoke_app.py` 里「加一卷后原有 810 个 `MixRecipe` 对象**还是同一批**」
的身份检查（`is` 比较，不是相等比较）。


## 16. 启动那一秒：先出窗口，再算混色表

### 16.1 问题

`MainWindow.__init__` 里就调用 `_reload_library()`，于是**第一次**整表计算
（41 卷 3.1 s，加上建控件约 1.3 s）全部发生在窗口出现之前。用户双击图标后
要盯着桌面 4.4 秒才看到窗口 —— 又是一次「这程序是不是死了」。

### 16.2 做法：`defer_build`

`MainWindow(library, parent, *, defer_build=False)`。真正的启动器
（`app/main.py` 的 `main()`）传 `defer_build=True`：

```python
window = MainWindow(defer_build=True)   # 0.2 s 就建好了，还没算混色
window.show()                           # 窗口立刻出现
return app.exec()                       # 事件循环里再算
```

`_rebuild_catalog()` 遇到 `_defer_build` 时**不往下算**，改为：

1. `_announce_build()` —— 状态栏写「正在计算 66,420 个混色，请稍候…」，
   网格里写「正在计算混色表…」，挂上等待光标，`processEvents()` 让它先画出来；
2. `QTimer.singleShot(BUILD_DELAY_MS, self._rebuild_catalog)`，并把
   `_defer_build` 清掉，所以第二次进来走正常路径。

**为什么不是 `singleShot(0, …)`**：0 毫秒的定时器会**抢在 `show()` 投递的
重绘事件前面**执行，窗口照样要等算完才出现，等于没改。`BUILD_DELAY_MS = 150`
就是给重绘留出的窗口。

**测试和命令行工具不受影响**：`defer_build` 默认 `False`，
`smoke_app.py` / `selftest.py` 里 `MainWindow(library=…)` 仍然是同步建表，
不用等定时器。`tools/smoke_app.py` 里另有一组检查专门构造
`defer_build=True` 的窗口，断言「先出窗口、状态栏说在算、网格不冤枉用户」，
再跑事件循环确认表最后建好了、等待光标收回、网格提示复位。

### 16.3 顺带修的一处谎话

网格空的时候默认写「还没有混色。请先添加至少两种耗材。」。计算还没开始时
这句话是**假的**（耗材明明有 41 卷）。`MixGrid.setEmptyText(text)` 让它
在计算期间改说「正在计算混色表…」，算完复位。

界面见 `samples/startup-calculating.png`。


## 17. 看不见的标签页不用算

### 17.1 问题

「图片转模型」页载入图片之后，每次改动耗材库都会**重新匹配**一次
（`PicturePage.setLibrary` → `_on_rematch`）。41 卷时候选有 66,461 个，
重新匹配约 **0.7 s**，加上整表同步和网格重排，在「颜色配方」页上
每加一卷耗材要等 **1.34 s** —— 而这张计算结果画在**另一个标签页**上，
用户根本看不见。

### 17.2 做法：借条

`PicturePage` 多一个 `_stale` 标记。`setLibrary()` 里：

```python
if self._image is None:
    return
if not self.isVisible():        # 当前显示的是「颜色配方」页
    self._stale = True          # 记一笔账，先不算
    return
self._on_rematch()
```

`showEvent()` 里补账：

```python
if self._stale:
    self._stale = False
    self._on_rematch()
```

`QTabWidget` 会把非当前页 `hide()` 掉，所以切过去时 `showEvent` 一定会响；
真正要看的时刻才付这 1 秒。

### 17.3 实测（41 卷 + 已载入图片）

| 场景 | 耗时 |
| --- | --- |
| 在「颜色配方」页改一次耗材库 | **0.219 s**（原来 1.336 s） |
| 切回「图片转模型」页补做匹配 | 1.107 s |

每次编辑省下 **1.118 s**。


## 18. 候选颜色表只建一次

### 18.1 问题

`build_palette()` 在 41 卷时产出 **66,461** 个 `PaletteEntry`，要 **0.33 s**。
它被两个地方各自调用了：

* 每次「重新匹配」；
* 每点一次「更换颜色…」。

也就是说，用户连续换三四个颜色，就要重复建表三四次。

### 18.2 做法：`PicturePage._candidate_palette()`

```python
if self._candidates is None:
    self._candidates = build_palette(self._library, self._catalog, include_mixes=True)
return self._candidates
```

缓存键原本要带上「混色也算候选」这个勾选状态，勾选框一动就得重建。1.6.10 把
那两个勾选框整个删掉了：候选池永远包含本色、两色混色和三色混色（见 §35），
所以现在只剩「建过没有」这一个判断，不可能再读到过期的表。`setLibrary()` 里把
`self._candidates = None` —— 耗材库一变就作废（这个方法本来每次编辑都会走）。

### 18.3 实测（41 卷，66,461 个候选）

| 场景 | 改动前 | 改动后 |
| --- | --- | --- |
| 打开「更换颜色…」 | 0.475 s | **0.186 s** |
| 重新匹配（表已缓存） | — | 少掉建表的 0.33 s |

顺带把搜索框里那一层「每格重新拼名字」也缓存了（`_filament_haystack`）：
66,420 个混色 × 两个母材，每个键位的字符串拼接原本要重做一遍。
收益不大（约 0.05 s）但代码更直白。


## 19. 导出那两秒也要说话

`buildPlate()` 在 512×512、12 色的图上要 **1.97 s**，`write_3mf()` 再
**0.37 s**。以前这两步之间界面上**什么都没有** —— 又是「未响应」的配方。

## 20. 混色表本身也快了 4 倍

§16 让启动时的 3 秒变得**看得见**，§15 让加/删一卷不再整表重算。
剩下最实的一块是那次首建本身 —— 41 卷 66,420 个混色，
`MixCatalog.build()` 原先 **3.14 s**。

### 20.1 先量，别猜

拿 `presets/大简-PETG-HF-耗材档案.json` 逐段计时：

| 阶段 | 1.2.10 |
| --- | --- |
| `engine.mix_rgb`（混色多项式） | **2.659 s** |
| `color.lab_from_rgb` | 0.020 s |
| 拼 `#RRGGBB` 字符串 | 0.070 s |
| 构造 66,420 个 `MixRecipe` | 0.541 s |

直觉会怀疑那 66,420 个 dataclass，实际不是：**多项式本身占了 85%**。

### 20.2 病根：`np.power` 被调用了上百万次

`app/spectral/filament_mixer.py` 里原本这样算 330 个特征：

```python
features[:, mask] *= x[:, column:column + 1] ** exponents
```

`exponents` 是**向量**，于是 NumPy 对每个元素单独调一次 `pow()`。
330 个单项式里变量出现约一千次，66000 行就是**几千万次 `pow`**。

### 20.3 做法：按「父项」乘出来，并把系数一起重排

330 个特征正好是 7 个输入的**全部 4 次及以下的单项式**
（`1 + 7 + 28 + 84 + 210 = 330`）。所以每个单项式都有一个自然的父项：
**把最高次那一项去掉**。父项的值再乘上该输入的整幂就是它。

`_build_layout()` 按「最高非零输入编号 → 该输入的指数」分组遍历，
组内按父项位置排序后**连续地**追加到布局里：

```python
features[:, start : start + count] = (
    features[:, parents] * np.power(x[:, index : index + 1], exponent)
)
```

每个特征只做一次乘法，330 列一共 330 次；`x ** e` 只算 330 次而不是几千万次。

因为输出列的顺序被换过了，**系数矩阵也跟着换一次**
（`COEF_ORDERED = COEF[_ORDER]`），多项式本身完全没变。
父项链正好是子项链去掉最后一个因子，所以**连浮点舍入顺序都和原来一致** ——
改完之后 66,420 个混色与改动前的输出**逐位相同**（用 `_mixer-baseline.npy`
对比过 199,260 个数值，零差异），`tests/test_engine.py` 里的
`MixerFeatureLayoutTests` 现在把这件事钉住。

### 20.4 结果

| | 1.2.10 | 1.2.11 |
| --- | --- | --- |
| 特征矩阵 + 多项式 | 2.68 s | **0.28 s** |
| `MixCatalog.build()`（41 卷 66,420 个） | 3.14 s | **0.82 s** |
| 启动后那段「正在计算…」 | 2.1–3.8 s | **0.70–0.80 s** |

`_CHUNK` 也从 200,000 降到 2,048：一次要写的 330 列矩阵从 175 MB 降到
5 MB，正好落进缓存，实测再快一倍（这段与取值无关，所以可以放心调）。


## 21. 100 卷耗材时会怎样（实测，不是推测）

41 卷是「大简 PETG HF」预置档的规模，但导入是追加的，用户很可能再往上堆。
所以拿一份**随机生成的 100 卷**档案（`C(100,2) = 4,950` 对 × 81 =
**400,950** 个混色）从头到尾量一遍，确认没有会崩或者会卡死的地方：

| 阶段 | 41 卷（66,420 个混色） | 100 卷（400,950 个混色） |
| --- | --- | --- |
| `MixCatalog.build()` | 0.82 s | **5.43 s** |
| `sorted_recipes('rgb')` | 0.07 s | 0.32 s |
| `build_palette(include_mixes=True)` | 0.33 s | **3.13 s** |
| 窗口出现（构造 + `show()`） | 0.98 s | 6.66 s |
| `match_image(12 色)` | 0.70 s | 1.30 s |
| 打开「更换颜色…」对话框 | 0.19 s | 0.70 s |
| 「更换颜色…」里第一次搜索（含建索引） | 0.25 s | **1.97 s** |
| 之后每次搜索（只过滤） | 0.08 s | 0.43 s |
| 网格总行数 | 66,420 | **400,950** |

结论：

- **没有崩、没有算错、没有丢行。** 400,950 行网格照样是全量虚拟绘制，
  滚动不卡；`MixGrid._rows` 本来就没有上限。
- `MixCatalog.build()` 的 5.43 s 是**报出来的**（§16 的「正在计算…」），
  不是假死。
- 「更换颜色…」对话框只实体化 200 行，401,050 个候选也是 0.70 s 打开。
- 第一次搜索那 1.97 s 是**一次性**建搜索索引（`_haystack_table()`，
  每个候选一条小写字符串，混色还要算上它两个母材的名字 / 品牌 / 种类 / 备注），
  建完缓存在 `self._haystacks` 里：同一查询再搜一次 0.43 s，
  换一个查询也是 0.43 s（实测），也就是只剩一次纯过滤。
- 剩下最实的一块是 `build_palette()` 的 3.13 s —— 它只在第一次
  「重新匹配 / 更换颜色」时发生，之后由 §18 的缓存挡住。
  41 卷时它是 0.33 s，用户感觉不到。

也就是说：这个程序的瓶颈都集中在**首次建表**，而且都有进度提示；
日常增删改查都在零点几秒以内。

## 22. 完全相同的混色合成一个颜色

### 22.1 问题

两个不同的配方经常算出**同一个 `#RRGGBB`**。极端例子是耗材本身就很接近的时候：
`#F7F3F3` 和 `#2C2A2C` 以各种比例混，会不止一次落到 `#8F8F8F` 上。
以前网格里这些格子一个不少地排着，用户看到一片同色方块，
点进去也只看到一个配方 —— 「这个颜色到底是怎么调出来的」反而更难回答了。

### 22.2 做法

`mixes.py` 里新增 `MixColour`：

```python
@dataclass(frozen=True)
class MixColour:
    rgb: tuple[int, int, int]
    color_hex: str
    lab: tuple[float, float, float]
    recipes: tuple[MixRecipe, ...]   # 所有能混出这个颜色的配方
    pair_index: int = -1

    @property
    def ratio_text(self) -> str:
        return f"{self.recipe_count} 个配方" if self.recipe_count > 1 else self.first.ratio_text
```

`merge_recipes(recipes)` 按 `color_hex` 分组，组内保留 `rgb` / `lab`、
`pair_index` 取最小值，最后按 rgb 排序。`MixCatalog._remerge()` 在
`build()` 和 `sync()` 的末尾各调一次（**不放在 `_compute_pairs` 里**，
否则每加一卷耗材会把整表重新分组）。

`MixColour` 故意暴露出和 `MixRecipe` 一样的只读属性名
（`key` / `rgb` / `lab` / `lightness` / `hue` / `chroma` / `pair_index` / `a_id` / `b_id`），
所以 `sorted_cells` / `recipe_sort_key` / `MixGrid` 一行都不用改 —— 颜色和
单条配方排在一起，排序规则自然一致。

### 22.3 实测（41 卷大简 PETG HF）

| | 数量 |
|---|---|
| 配方 | 66,420 |
| 去重后颜色 | **59,648**（合并率 10.196 %） |
| 只有 1 个配方的颜色 | 54,781 |
| 2 个 / 3 个 / 4 个 / 5 个 / 6 个配方 | 3,918 / 605 / 168 / 76 / 29 |
| 最多配方的颜色 | `#8F8F8F`，**18 个配方** |
| 合并耗时 | 0.001 s |

### 22.4 详情面板要列出所有配方

`MixDetail` 原来只认识「一条配方」，两行母材是写死的（`for slot in (1, 2)`）。
现在多了 `showColour(colour)`：先照旧 `showRecipe(recipes[0])`
（预览色块、比例条、「在 Bambu Studio 里这样复现」都描述第一条），
再在下面补一个标题「合成 `#8F8F8F` 的所有配方（18 条）」和一张配方清单，
每行 `名称 (#hex) 百分比 + 名称 (#hex) 百分比`。
超过 `MAX_RECIPE_ROWS = 50` 条时只列前 50 条并注明还有多少条没显示。
`selectionKey()` 优先返回 `colour.key`，所以刷新网格后选中的仍是这个颜色，
不会退回到某一条配方。

### 22.5 踩过的坑：详情面板被压扁

18 行配方让详情面板比窗口还高，而它当时是 `QSplitter` 的直接子控件 ——
**splitter 空间不够时是把子控件压扁，不是给它滚动条**。
更糟的是配方行的文字开了 `setWordWrap(True)`，自动换行的 `QLabel`
`minimumSizeHint()` 很小，于是布局把每一行压到 **3–4 px**，
18 行全部叠印在一起。

两处一起改：
1. `main_window.py` 把 `MixDetail` 包进 `QScrollArea(widgetResizable=True)`，
   面板恢复成它真实需要的高度（实测 `minimumSizeHint` 从 997 变成能被滚动），
   主窗口的 `minimumSizeHint().height()` 也从 1290 掉回 558；
2. 配方行的文字**不换行**（`setWordWrap(False)`），整列才有真实的最小高度。

顺带把 splitter 的第三格从 400 加宽到 440，否则「预测颜色 #8F8F8F RGB 143, 143, 143」
最后一位会被裁掉（截图 `samples/merged-colour.png`）。



## 23. 三色混色：2122 万个颜色怎么放得下

### 23.1 2556 是怎么来的

三卷耗材按 **1 % 步进**混合，`a + b + c = 100`，每种至少 10 %。
因为三者之和固定，另外两个 ≥ 10 就自动让每个 ≤ 80，所以只写下限即可：

```
a' = a - 10, b' = b - 10, c' = c - 10  ->  a' + b' + c' = 70
解的个数 = C(70 + 3 - 1, 3 - 1) = C(72, 2) = 2556
```

10 % 步进只有 36 个，5 % 步进只有 120 个 —— **2556 只能是 1 % 步进**。
交换用量算不同配方，所以 `30/40/30` 和 `40/30/30` 是两条。
`triple_ratios()` 就是这张 `(2556, 3)` 的表，`TRIPLE_RATIO_COUNT = 2556`。

混色本身不用新算法：`filament_mixer.mix_rgb` 已经把 `K` 卷**从左往右依次合成**，
先按 `w0 : w1` 合成前两卷，再把结果按 `w2 / (w0 + w1 + w2)` 与第三卷合成 ——
这就是 Bambu Studio 的三色算法。实测 `mix_rgb(K=3)` 在第三卷为 0 % 时
得到的颜色与 `mix_rgb_pair` 两色路径完全一致。

### 23.2 规模：41 卷 = 2122 万个颜色（实测）

| 卷数 | 三卷组合 | 配方 | 去重后颜色 | 耗时 |
|---|---|---|---|---|
| 6 | 20 | 51,120 | 32,652 | 0.50 s |
| 10 | 120 | 306,720 | 199,680 | 2.59 s |
| 41 | 10,660 | **27,246,960** | **4,295,101** | 224 s 混合 + 7.3 s 排序 |

合并率 15.764 %。**430 万个颜色不可能每个都建一个 Python 对象**
（`MixGrid._relayout` 光是把单元格索引存成 `list[list[int]]` 就要约 150 MB），
所以三色表是 numpy 的，不是对象列表。

### 23.3 存储：一张排序数组 + 一条 CSR 索引

`TripleCatalog` 里只有四个数组：

| 数组 | 类型 | 含义 |
|---|---|---|
| `packed` | `int32[C]` | 去重后的颜色，`(r<<16) \| (g<<8) \| b`，升序 |
| `_offsets` | `int64[C+1]` | CSR 偏移，第 i 个颜色占 `_codes[_offsets[i]:_offsets[i+1]]` |
| `_codes` | `uint32[M]` | 配方编号 `triple_index * 2556 + ratio_index` |
| `_labs` | `float64[C][3]` | 用到才算，算一次缓存 |

`finish()` 一次做完：`np.argsort(packed, kind="stable")` →
相邻不等即为分组边界 → `np.flatnonzero` 得 `_offsets`。
去重不丢配方：`recipe_count_at()` 之和恒等于 `recipe_count`。

### 23.4 界面：几百万个格子怎么画

`TripleColours` / `OrderedTripleColours` 是 `Sequence`，
`__getitem__` 才把某个颜色实例化，`index_of_key()` 用
`np.searchsorted(packed, …)` 做 **O(log n)** 定位（不是扫描）。

排序同样不物化：`order()` 返回 `np.lexsort` 的**下标数组**，
`OrderedTripleColours` 只是把下标映射过去。

`MixGrid` 超过 `LAZY_LIMIT = 120_000` 个格子就切换成**算术布局**：
不再维护 `_rows: list[list[int]]` 和 `_row_y`，
而是 `行 = index // columns`，`paintEvent` 只画可见行，
`_indexAt` 直接 `int(y // CELL)` 反算。分组间距在这种模式下省略 ——
排序本身已经把同一对母材排在一起了。

### 23.5 不卡窗口：切片计算 + 进度

224 秒不可能放在一次事件循环里。`build()` 被拆成
`begin()` → `step(budget_seconds)` → `finish()`：
`step()` 每次只混合 24 个组合，超过时间预算就返回 `False`。
窗口用 `QTimer(interval=0)` 反复调 `step(0.18)`，
状态栏实时写「正在计算三色混色：x / 27,246,960（n%）」，
期间界面照常重绘。算完再存缓存、刷新网格。

### 23.6 缓存：第二次打开不用再等 224 秒

缓存键是 `sha256("triples-1|引擎|下限|id:颜色"…)` 的前 16 位，
**耗材库或引擎一变，键就变**，不会读到过期结果。
文件是 `数据目录/cache/triples-<key>.npz`，先写 `.tmp` 再 `os.replace`，
写坏了下次重建即可（`load_triple_cache` 捕获异常返回 `None`）。

### 23.7 导出时把混色表一起带走

按需求，**导出耗材档案时也把算好的混色表导出去**，这样换机器或者重装之后
导入一次就不用再等 249 秒。

混色表放不进 JSON：41 卷的缓存是

| 数组 | 大小 |
|---|---|
| `packed` | 17,180,404 B |
| `offsets` | 34,360,816 B |
| `codes` | 108,987,840 B |
| 合计（`npz`） | **160,688,896 B（153.2 MB）** |

而耗材档案本身只有 11,788 B。整数数组用 `npz` 压不动（实测压缩前后一模一样），
所以做法是**在旁边多写一个同名文件**：导出 `耗材档案.json` 时，
只要三色表已经算好，就再写一个 `耗材档案.mixes.npz`
（`mix_sidecar_path()`）。没有算过三色混色就只写 JSON。

缓存里额外存了一个 `key` 字段，记着它属于哪一套耗材
（`triple_cache_key()` 的结果）。导入时先算当前耗材库的键，
**对得上才认领**，对不上就丢掉 —— 免得把别的耗材库的混色表套到自己头上。
认领成功时顺手把它写进本机缓存，同时把界面切到三色混色模式。

### 23.8 暂时不做的事

- **三色混色时搜索框和「全部颜色」都禁用**：4.3 M 个颜色逐个套名字不可能，
  而耗材本色也没法在保持排序的前提下插进一个 430 万长的惰性序列里。
  取消勾选「三色混色」即可恢复。
- 两色表仍然是对象列表（59,648 个），因为它的规模完全承受得住，
  只有三色表走 numpy 路径。


## 24. 那份 153 MB 的缓存谁来收拾

§23 的结论是「把三色表缓存到磁盘」。缓存名是
`triples-<耗材库+引擎的指纹>.npz`，于是有个不显眼但会积累的坑：
**指纹一变，旧文件就永远没人读，但也不会自己消失。**

加一卷耗材、改一个颜色、换个混色模型，都会换一个键；41 卷时每换一次
就多留 **153 MB**。编辑十次就是 1.5 GB。

### 24.1 留最近三份

`prune_triple_caches(directory, keep=3)` 扫目录，按修改时间倒序，删掉第 4 份
往后的 `triples-*.npz`，顺手清掉上次崩溃留下的 `.tmp`。
每存一份新缓存就调用一次（`save_triple_cache()` 只对 `triples-` 前缀生效，
所以导出档案旁边的 `xxx.mixes.npz` 不会牵连到别人的缓存）。
命中缓存那一条路径也会调用一次 —— 否则只读不写的用户永远等不到清理。

保留三份而不是一份，是因为在几套耗材之间来回导入导出时，
上一套的表还在，切回去不用重算那 249 秒。

### 24.2 指纹对不上就当没有

光靠文件名不够。极端情况：三色表算到一半时用户加了一卷耗材。
这时正在算的那张表是**旧的**，但写盘时的路径是**按新库算的**，
内容与名字对不上，下次打开就会把错颜色当对的用。

两道防线：

1. `load_triple_cache()` 读出来先比对 `key` 字段
   （`save_triple_cache()` 写入的 `triple_cache_key()` 结果），
   对不上直接返回 `None`；
2. `MainWindow._invalidate_triples()` —— 只要 `_rebuild_catalog()` 跑过
   （耗材库或引擎变了），就停掉正在跑的定时器、丢掉 `_triples` 与 `_triple_view`；
   如果「三色混色」还勾着，就用新的耗材库重新开始算。

`tools/smoke_app.py` 里加了对应的一条：在三色模式下加一卷耗材，
断言颜色数确实变了（不是留着旧表），再把耗材删回去。


## 25. 「删除 / 合并 / 撤销」为什么不用碰像素

「图片转模型」页要支持三件事：**删除**（这块留空、不打印）、**合并**
（几种颜色并成一种再打印）、以及撤销 / 恢复。最直接的写法是把
`MatchResult.indices` 改掉——删就把那些像素写成 `-1`，合并就把源下标改成
目标下标。但那样有三个问题：

1. 撤销需要一份历史。`indices` 是 H×W 的 int32，1024×1024 就是 4 MB，
   存 64 步是 256 MB；
2. 「更换颜色」和「删除」会互相踩：先删了 A，再撤销一次替换，
   删掉的 A 就复活了；
3. 合并是**有向**的（A→B），一旦把像素写死，就再也分不出
   「本来就是 B」和「并过来的」。

所以编辑状态只存三个小字典，**永远从原始匹配结果重算**：

| 状态 | 内容 |
| --- | --- |
| `_base` | 匹配器算出的原始 `MatchResult`，永不修改 |
| `_deleted` | 被删掉的颜色（原始下标）集合 |
| `_merged` | `源下标 -> 目标下标`，原始下标 |
| `_replaced` | 手动「更换颜色」的结果，原始下标 -> `PaletteEntry` |

`_compose()` 每次从头重建：先 `_resolve()` 把 `_merged` 的链走完
（A→B、B→C 就是 A、B 都打 C），再把目标已被删除的源一起标成消失，
然后 `np.array(base.indices, copy=True)`，合并的改下标、删除的写 `-1`，
最后按 `base.palette` 的原顺序挑出还活着的颜色、重排下标、
用 `np.bincount` 数一遍像素数，交给 `dataclasses.replace()` 生成新的
`MatchResult`。

一次编辑的成本是「一份 H×W 的拷贝 + 十几次布尔掩码」，41 卷 1024×1024
的图上每次 `_apply_edits()` 大约 **8 ms**，所以按钮是按下去就生效的，
不需要任何进度条。撤销栈里存的是
`(set(_deleted), dict(_merged), dict(_replaced))` 的快照——最多几十个整数，
64 步也就几十 KB。

### 25.1 透明这条路早就铺好了

删除不需要改任何网格代码。`mesh/plate.py` 的 `build_plate()` 本来就是：

```python
silhouette = result.indices >= 0          # 底板轮廓
mask = result.indices == index            # 每种颜色的棱柱
```

也就是说 `-1` 的像素**本来就不在轮廓里**，因此那一块既没有底板、
也不属于任何一个颜色的棱柱——删掉一块，模型上就是一个真正的洞。
唯一的例外是整张图都被删光：`palette` 为空时 `build_plate()` 抛
`ValueError("没有一个可打印的颜色，无法生成模型。")`，
界面把它原样显示给用户，而不是崩掉。

### 25.2 三个不显眼的坑

* `MatchResult.region_colour(index)` 读的是 `means[index]`。
  重排下标时必须把 `means` 一起重排，否则调色板对了、色差数字是别人的；
* `_compose()` 里 `alive` 的判据是「不在 `_deleted` 且**不是合并的源**」，
  不是「像素数大于 0」——一个颜色被并走之后像素数是 0，但
  它自己的下标还在 `indices` 里出现过，靠数像素判断会把它留下；
* 高亮时 `PictureView` 原本把整张画布 alpha 写 255，于是删掉的区域
  一高亮又变成实心。现在只有 `indices >= 0` 的像素才铺那层淡灰，
  删掉的地方始终保持透明。

## 26. 「找最接近的颜色」为什么会答错

用户问的是 `#FFFFFF`，程序答的是 `#E5E5E5`（ΔE00 5.40）——而纯白
`#FFFFFF` 就明明白白摆在同一个网格里，ΔE00 = 0。错在 `nearest_recipe()`
里那两句**故意的过滤**：

```python
# 旧代码：只要「真正的混色」，跳过耗材本色
if cell.recipe_count:            # 合成表分支
    return cell
...
if cell.pair_index >= 0:         # 短列表分支
```

写这两句的动机是「用户想要的是混色吧」——但这是猜测，不是需求。
**耗材本色是最准的答案**：他手里就有这卷料，根本不用混。
所以现在全表都是候选，一个都不跳。

去掉过滤之后，性能问题就冒出来了：三色表是 2122 万个颜色，逐个算
CIEDE2000 是不可能按下去的。好在排序器早就有现成的答案：

* `CombinedColours.order(SORT_SIMILARITY, target)` 对**整张表的 Lab**
  做一次 `np.argsort(delta_e_2000(lab, target), kind="stable")`
  （`app/core/triples.py`），排完的**第一个就是最近的**，不需要什么
  「取前 16 个再挑一个有配方的」这种近似；
* 搜索框把表缩小之后，`order` 仍然是全表的顺序，所以只做一次
  `order = order[np.isin(order, view.indices)]`——掩码保持顺序，
  第一个活下来的依然是**当前看得见的那些里最近的**。
  这就是 `OrderedCombinedColours.indices` 存在的唯一理由。

短列表（某一对的 81 个配比）没有 Lab 表可排，就老老实实逐个
`delta_e_2000()` 量一遍——81 次而已。

答案是不是混色，界面要分开说：`recipe_count` 为 0 就写
「最接近 #FFFFFF 的颜色**就是耗材本色** #FFFFFF（色差 ΔE00 = 0.00）」，
否则写「最接近 … 的颜色是 …」。按钮原来叫「找最接近的混色」，
这个名字本身就是那个 bug 的来源，现在叫「**找最接近的颜色**」。

### 26.1 「原图」为什么不跟着高亮

「图像转换」页左边那块叫**原图**，右边那块叫**预览**。点右边的颜色时，
原图整张都会被洗成淡灰——用户报的就是这个：「原图改成用户上传的图片」。

原因不在 `setShowMatched(False)`（那句是对的，`_base_image()` 确实返回
上传的原图），而在 `paintEvent` 画完底图之后又无条件叠了一层
`_dim_pixmap()`：它把「印出来的、但不是当前选中色」的像素全部涂成
`(246, 247, 249, 168)`。选中一个颜色，原图就被涂花了。

修法是给 `PictureView` 加一个**素模式** `_plain`：

```python
def setSelected(self, index):
    if self._plain:      # 原图不参与选中
        return
    ...

def _dim_pixmap(self):
    if self._plain:      # 原图从不被洗淡
        return None
    ...
```

`setPlain(True)` 还会顺手把 `_selected` / `_highlight` 清掉，并让
`mousePressEvent` 直接返回——原图是拿来对照的，点它不该有反应。
预览那边一点没变，`_plain` 默认是 `False`。

### 26.2 一条说明文字为什么能把窗口钉死

「每两种耗材 81 个配比（10%–90%）· 三色混色：… · 共 10,710 个配比 · …」
原来是网格面板底部的一个 `QLabel`。它**没有开自动换行**，而 Qt 对
不换行的 `QLabel` 算 `minimumSizeHint().width()` 的方式，就是**整行文字的
宽度**——于是这个标签的最小宽度成了 1400 px，中间那一栏再也压不下去，
`QSplitter` 的拖动条只能「啪」地跳到另一个位置，看起来像拖不动。

所以这条说明搬到了**底部**，并且给标签设了

```python
self._status.setWordWrap(True)
self._status.setSizePolicy(QSizePolicy.Policy.Ignored, QSizePolicy.Policy.Minimum)
```

`Ignored` 的意思是「窗口变窄时尽管压我」，它于是只会折行、不会顶宽窗口。
当时还把完整文字塞进了一份 tooltip，怕用户没看全；**1.6.10 把那层 tooltip 整个删掉了**
（见 §36.5），现在这一行就是唯一的出口，所以它必须自己站得住。

**这里踩过一次坑，值得记下来。** 第一版把它放在 `QMainWindow` 的
`QStatusBar` 里，只设了 `Ignored` 却没设换行。`Ignored` 解决了「顶宽窗口」，
却没解决「装不下」：状态栏只有一行高，1020×640（程序的最小尺寸）下这句话
在第一个中文字符的中间被硬切掉，连省略号都没有。`setWordWrap(True)` 单独
也救不了——`QStatusBar` 不会因为子标签变高就长高。

所以它现在是**页面主体布局的最后一行**：

```python
layout.addWidget(tabs, 1)
layout.addWidget(self._status)
```

`QLabel` 开了换行之后 `hasHeightForWidth()` 为真，`QVBoxLayout` 会照着折行后的
高度给它让位，第二行就完整露出来了。代价是 `QMainWindow` 从此不再创建状态栏
（也就没有了右下角那个拖拽改窗口大小的小三角），换来一句话任何时候都读得全。

再往后一步：这句话讲的是颜色表，那么在**「图像转换」页就是废话**——而且那一页
自己上边已经有一条状态行了。所以 `_tabs.currentChanged` 接到 `_on_tab_changed`，
切页时重新算一次，当前页不是「颜色配方」就把 `note` 置空。

顺带一提，网格面板下部原来还有一行「耗材 5 种 · 母材组合 10 对 · 混色 810 个
· 去掉重复后 809 个颜色 · 计算用时 4 ms」，和这条说明说的是同一件事，
现在合并成一行。

### 26.3 让标签「可以被鼠标选中」这件事

用户要的是「鼠标可以选择文本，方便复制」——提示、配方、状态栏、右侧
「在 Bambu Studio 里这样复现」那一段，全都要能拖选。

给每个面板调一次 `selectable_text(root)` 能覆盖大部分标签，但**覆盖不全**：
配方行是选中某个颜色时才现做出来的（`_make_formula_row()`），构造界面时
它还不存在。所以 `app/ui/selectable.py` 里还有一个挂在 `QApplication` 上的
事件过滤器：

```python
def eventFilter(self, obj, event):
    if event.type() == QEvent.Type.ChildAdded and isinstance(event.child(), QLabel):
        event.child().setTextInteractionFlags(SELECTABLE)
    return False          # 从不吞事件，界面行为一点都不改
```

任何 `QLabel` 一出生就自动变成可选中，以后新加的标签不会再漏掉一个。
只动 `QLabel`：按钮、输入框、列表本来就能选能复制，改了反而会抢走
单击 / 双击这些交互。

（应用层的过滤器在 `build_application()` 里装一次，三个入口共用。）

## 27. 「删除 / 合并 / 撤销 / 恢复」四个按钮为什么一直是灰的

用户报的是「这四个按钮按不了」。它不是四个 bug，是**一个** bug，而且是一个
两行代码打成的死结。

`ColourList` 里有两个东西在互相问对方要答案。一个是 Qt 列表自身的选择状态，
一个是缓存的集合 `self._picked`：

```python
# 旧代码，picture_page.py
def selected_indices(self) -> list[int]:
    live = {...}
    return sorted(index for index in self._picked if index in live)   # 问 _picked

def _on_selection_changed(self, *_) -> None:
    self._picked = set(self.selected_indices())                      # 又问回去
```

`selected_indices()` 从 `_picked` 里挑，`_on_selection_changed` 再把结果写回
`_picked`。**没有任何一行代码去读 `QListWidget` 真正的选择状态**，所以
`_picked` 从程序启动到关闭永远是空集。`_update_actions()` 里那句
`len(picked) == 0` 于是永远成立：

- 删除、合并永远灰着；
- 一个编辑都做不出来，撤销栈就一直是空的，撤销、恢复也跟着永远灰着。

这就是「四个按钮按不了」的全部原因。修法是把信息流向反过来，只让 Qt 当唯一
的真相来源：

```python
def selected_indices(self) -> list[int]:
    return [index for index, item in enumerate(self._items) if item.isSelected()]
```

再补一个 `select(indices)`，它调 `item.setSelected(...)` 而不是去改 `_picked`，
这样走的是 Qt 真正的 `itemSelectionChanged` → `_on_selection_changed` →
`_update_actions()` 链路。自动检查里原来直接写 `page._list._picked = {0, 1}`
的地方也全部改成了 `page._list.select([0, 1])`——**绕过界面的测试会把这类 bug
一直藏住**，这正是它当初活下来的原因：单元测试和 smoke 都在直接改 `_picked`，
于是都「通过」了。

教训一句话：一个状态有**两个**宿主时，必须有一个是只读的派生值；两个都可写
就会互相喂自己的旧值。

### 27.1 「恢复自动匹配」为什么删掉了

原来「选中的颜色」面板底下有一对按钮：绿色的「更换颜色…」和它的后悔药
「恢复自动匹配」。用户的要求是「删除恢复自动匹配，让撤销也可以撤销更换颜色」。

查过之后发现后悔药早就有了：`_on_replace()` 在写入 `self._replaced[原色] = 新色`
**之前**先调了 `self._push()`，而 `_snapshot()` 返回的是

```python
(set(self._deleted), dict(self._merged), dict(self._replaced))
```

`_replaced` 本来就在快照里，所以 **Ctrl+Z 早就能把手工换的颜色退回去**。
「恢复自动匹配」只是同一件事的第二个按钮，而且它的名字会让人以为「撤销」
不管换色——正好和事实相反。于是把它删掉，同时把那一行文字改成
「按 Ctrl+Z（或点「撤销」）可以退回来。」，并让 `_difference` 在撤销之后
自动回到「图片颜色与匹配颜色的差距 ΔE00 …」。

顺手把「更换颜色…」从面板底部搬到了页面下方那一排，顺序变成
**删除、合并、更换颜色…、撤销、恢复**：前三个是「怎么改」，后两个是「改错了
怎么办」，一条线读下来就是操作顺序。

### 27.2 为什么点耗材本色会挂着上一轮的「耗材丝3」

「颜色配方」面板固定有 3 行：耗材丝1 / 耗材丝2 / 耗材丝3。两色配方用 2 行，
三色配方用 3 行，**耗材本色只用 1 行**。

`showRecipe()` 是对的，它遍历所有行、把 `index >= len(parents)` 的都藏起来。
但 `showFilament()`（显示耗材本色那条路径）只藏了第 2 行：

```python
self._rows[1]["frame"].setVisible(False)      # 旧代码，漏了第 3 行
```

于是先点一个三色混色、再点一个耗材本色，第 3 行会**原样留着上一次的三色配方
内容**：`#FF0000` 的本色下面写着「耗材丝3 … 12%」，「耗材丝3」还显示着另一卷
料的颜色和百分比——看起来就像这卷红料是由它自己和一卷绿料混出来的。修法是
一次把第一行之后的**所有**行都藏掉：

```python
for spare in self._rows[1:]:
    spare["frame"].setVisible(False)
```

按「藏到够用」写代码，行数一改就会漏；按「藏掉多余的全部」写，行数以后增加也
不会出问题。

### 27.3 打开就最大化

`main()` 最后不再调 `window.show()`，而是：

```python
def show_main_window(window) -> None:
    window.showMaximized()
```

程序**不记忆窗口大小**，每次都满屏打开。理由是这个程序只有一件事要做：让你
在一张几千到几十万个格子的颜色表里挑颜色，越宽越好；默认开成 1320×840 只会
让人每次启动都先手动放大一次。之所以抽成一个函数而不是直接写在 `main()` 里，
是为了让自动检查能断言这条策略而不用真跑事件循环——检查里调的就是同一个
`show_main_window()`，然后断言 `starter.isMaximized()`。


## 28. 版本号只写一次：exe 文件属性与「关于」共用同一个来源

用户拿到的是 `BambuPalette-1.6.3-win64.zip`，解压开是一个 `BambuPalette.exe` 加
一堆 `_internal`。装了两三个版本以后，光看文件名分不出到底跑的是哪一版——所以
exe 的文件属性里必须写着版本号。

写法是在 `build/BambuPalette.spec` 里**从源码读版本**，而不是再手写一个常量：

```python
def app_version() -> tuple[str, tuple[int, int, int, int]]:
    text = (Path("app") / "__init__.py").read_text(encoding="utf-8")
    match = re.search(r'^__version__\s*=\s*"([^"]+)"', text, re.MULTILINE)
    if match is None:
        raise RuntimeError("app/__init__.py has no __version__")
    ...

VERSION_TEXT, VERSION_PARTS = app_version()
VERSION_INFO = VSVersionInfo(ffi=FixedFileInfo(filevers=VERSION_PARTS, ...), ...)
EXE(..., version=VERSION_INFO, ...)
```

三件事值得记下来：

1. **`EXE(version=...)` 可以直接收一个 `VSVersionInfo` 对象**。PyInstaller 6.22.3 的
   `__init__` 里就是 `if isinstance(self.versrsrc, versioninfo.VSVersionInfo)`，
   网上大量教程还在先生成一个临时 `.txt` 再传路径，那是老版本的写法。
2. **版本号必须在构建时就解析出来，而不是在运行时**。运行时读源码在冻结以后是
   读不到的；这里是读构建机上的源码，两边永远同一个号，不会出现「exe 属性写着
   1.6.2、程序里显示 1.6.3」这种对不上的情况——这也是为什么解析失败时直接
   `raise`，宁可构建崩掉也不发一个没有版本号的包。
3. 程序里那份文字同样来自 `app.__version__`。`MainWindow._about_text()` 的第一行是
   `f"...版本 {__version__}"`，`_on_about()` 只负责把它塞进 `QMessageBox`。**把
   文本抽成一个返回字符串的方法**，是为了让自动检查能直接断言「关于里写着当前
   版本」而不用去点开一个模态对话框。
4. **光写在文件属性里还不够**（1.6.3 就是这么做的，用户还是又问了一次）：文件属性
   要开资源管理器、右键、属性、切到「详细信息」才看得到，而用户判断自己装的是哪
   一版，看的是**眼前这个窗口**。所以标题栏直接写成
   `f"BambuPalette {__version__} — 混色耗材色彩管理器"`。同一份 `__version__`，
   三个地方（exe 资源、标题栏、关于对话框）各显示一次，谁也不会跟谁对不上。


## 29. 「多选」按钮：不改列表的选择模型，只是换个 `SelectionMode`

第二页要选中两三种颜色才能点「合并」。原来只能用 `Ctrl + 单击`，而 `Ctrl + 单击`
是**知道 Qt 才想得起来**的操作——用户不会去猜。

所以在「删除」前面加了一个**开关按钮**「多选」。它做的事只有一件：

```python
def setMultiSelect(self, on: bool) -> None:
    mode = (QAbstractItemView.SelectionMode.MultiSelection if on
            else QAbstractItemView.SelectionMode.ExtendedSelection)
    if self._list.selectionMode() == mode:
        return
    keep = self.selected_indices()
    self._list.setSelectionMode(mode)
    self.select(keep)          # 换模式时 Qt 可能把选择清掉
```

三个细节：

- **`MultiSelection` 和 `ExtendedSelection` 的区别只有「要不要按 Ctrl」**：
  `ExtendedSelection` 里单击是「替换选择」、`Ctrl + 单击` 才是「加一个」；
  `MultiSelection` 里单击就是「切换这一个」。两种模式下 `selected_indices()`、
  `itemSelectionChanged`、`_update_actions()` 全都不用改，因为它们本来就是从
  `item.isSelected()` 读的（见 §27 里那个死循环的教训）——**能不加状态就不加状态**。
- **换模式前后要把选择存下来再放回去**。`setSelectionMode()` 之后 Qt 有权把当前
  选择清空（视内部 selection model 的实现而定），不存一次就会出现「一开多选，
  刚选好的颜色没了」。
- **按钮自己变蓝是唯一的「开着」提示**。开关状态落在按钮上，和 `_update_actions()`
  驱动的可用性是两套东西：`多选` 永远是可用的，`删除 / 更换颜色` 要选了才亮，
  `合并` 要选两种以上才亮。整页只有右下角「生成 3MF」是常驻蓝色——它才是
  「干完了」的那个动作；把「更换颜色…」也涂成蓝色（1.6.2 及以前）会读成
  「这个才是重点」，而它其实只是这一排普通动作里的一个。
- **预览里的色块和清单里的行是同一批东西**，所以开着多选时点预览就是「把这一块
  加进 / 移出选择」（见 §30.3）。这件事没有第二套选择状态：预览点击最终调用的还是
  `item.setSelected()`。

## 30. 三个「点了没反应 / 点错了」的修复：借用目标、下一个、不要重排

用户报的三件事看着互不相干，根子上都是**「界面上做了一件事，但结果和用户以为的
不一样」**。

### 30.1 「找最接近的颜色」没填目标颜色就只印一句提示（1.6.2 及以前）

旧代码第一行就是：

```python
target = self._target_color.hex()
if not target:
    self._set_status_text("请先点「目标颜色」选一个想打印出来的颜色。")
    return
```

问题不在提示写得不好，而在**「点目标颜色」不是一个能做的动作**：程序里根本没有
弹出取色器（§见 README 第 8 条，那个色轮窗口在 1.6.0 就删了），`ColorField` 只有
一个 `#RRGGBB` 输入框和 R / G / B 三个数字框。所以这句话等于「请先做一件你做不到
的事」，用户看到的就是「按了没反应」。

改成**借用**，而且借来的东西必须写在明面上：

```python
target = self._target_color.hex()
borrowed = ""
if not target:
    current = self._grid.selectedRecipe()
    if current is not None:
        target = current.color_hex
        borrowed = f"你正看着的 {target}"
        self._target_color.setValue(target)      # 搜索必须打在看得见的地方
    else:
        r, g, b = self._target_color.rgb()
        target = _color.rgb_to_hex((r, g, b))
        borrowed = f"数字框里的 RGB {r}, {g}, {b}"
```

两条顺序就是**用户视线的远近**：先是他正在表里盯着的那一格，再是三个数字框里
摆着的数。结果行会补一句 `；目标颜色取自{borrowed}`，并且**把借来的颜色填回
「目标颜色」输入框**——一次搜索绝不能瞄向一个窗口上没显示的颜色，否则用户没
办法判断搜索结果对不对。原来那句 `if not len(self._recipes)` 的空库提示被挪到
了借用之后：空库和「没填目标颜色」是两件事，前者才是真的没得搜。

### 30.2 「添加耗材」一次只加一卷

`QDialogButtonBox` 会把 `ActionRole` 的按钮顶到整行的最左边，而用户要的是「下一个」
紧挨着「确认」左边。所以这一次没用按钮盒，自己拼了一行：

```
[下一个]  <伸缩>  [确认] [取消]
```

`下一个` 只是 `self._another = True` 然后 `self.accept()`——**它和「确认」走的是同一
条接受路径**，所以这一卷照样存下来；区别只在调用方 `MainWindow._on_add()`：

```python
while True:
    dialog = FilamentDialog(None, brands=…, types=…, parent=self)
    if dialog.exec() != FilamentDialog.DialogCode.Accepted:
        return
    ... 存入这一卷 ...
    if not dialog.wants_another():
        return
    # 回到循环顶部，新建一个空白表单
```

**每次循环新建一个对话框，而不是把旧的重置一遍。** 重置要记得把名称、品牌、种类、
颜色、备注、以及「颜色没填过」这个内部状态全部恢复成初始值，漏一个就会出现「上一
卷的品牌粘在下一卷上」；新建一个对象则天然干净，代价只是再 `exec()` 一次。

### 30.3 点一下清单，鼠标底下那一行变成了别的颜色

这一条是真 bug，而且是最隐蔽的一个。旧代码里 `ColourList.pin()` 是：

```python
self._order = [self._pinned] + [i for i in range(len(result.palette)) if i != self._pinned]
self._refresh()
```

**每一次单击都把整张表重排一遍，把点中的那一行挪到第 0 行。** 用户点的是第 12 行，
松手以后第 12 行已经是另一种颜色了——他看到的正是「点一个颜色，结果换成了另一个
颜色」。

修法是把「把这一行置顶」和「把这一行高亮出来」拆开：

- `pin(index)` 默认**不动顺序**，只记 `self._pinned`，然后 `_reveal()`；
- 只有样例截图需要旧效果，所以留了显式的 `pin(index, reorder=True)`。

`_reveal()` 负责把当前行高亮并滚进可视区，而它里面有一个**必须按模式分支**的坑：

```python
multi = self._list.selectionMode() == QAbstractItemView.SelectionMode.MultiSelection
keep = self.selected_indices() if multi else []
self._suppress = True
self._list.setCurrentRow(row)
self._list.scrollToItem(self._list.item(row), QAbstractItemView.ScrollHint.EnsureVisible)
self._suppress = False
if multi:
    self.select(keep)              # 多选：用户自己选的那一堆必须留着重放回去
else:
    self._on_selection_changed()   # 单选：setCurrentRow 选中的就是新的选择
```

第一版写成「不分模式，先把 `keep` 存下来、`setCurrentRow` 之后再 `select(keep)` 放
回去」，结果**把 `setCurrentRow` 刚刚选中的那一行又清掉了**：`keep` 是在
`setCurrentRow` 之前读的，那时可能一个都没选，于是放回去的是一个空集合。表现出来
就是 `删除 / 更换颜色` 又变灰——和 §27 那个死循环的症状一模一样，只是这次是另一个
原因。**「恢复旧状态」和「接受新状态」是互斥的两种意图，不能用一个 `keep` 同时表
达。** 单选模式下 `setCurrentRow` 本身就是选择动作，所以要的是后者；而它是在
`_suppress` 里跑的（`_on_selection_changed()` 会提前 return，否则 `_refresh()` 里
`setCurrentRow` → `currentRowChanged` → `_refresh()` 递归到爆栈），所以结束后要手
动补一次 `_on_selection_changed()` 把缓存和按钮刷出来。

同一个 `_reveal()` 还顺手把 `_refresh()` 结尾那句 `setCurrentRow(0)` 换掉了：删掉
一种颜色、合并几个颜色之后行号会整体前移，`0` 已经不是用户原来那一行了。

### 30.4 顺带：预览里的点击

```python
def _on_region_clicked(self, index: int) -> None:
    if self._multi_button.isChecked():
        self._list.toggle(index)
    self._select(index)
```

`toggle()` 就是 `item.setSelected(not item.isSelected())` 然后 `_reveal()`。预览和
清单显示的是同一批色块，用户在图上指哪一块，就是想让那一块进选择——没有理由逼他
再去右边一列里找对应的行。关掉多选时这一句不起作用，点预览仍然只是「看看这一块
是哪一种颜色」。

自动检查方面：`tools/smoke_app.py` 从 342 项涨到 **368 项**，`app --selftest` 同步
加了「标题栏带版本号」「没填目标颜色也会去搜、并说明借的是哪一个」「下一个紧挨
着确认且真的能连续加」「多选时点预览能加也能减」「点一下清单顺序完全不变」这
几条断言。

## 31. 三个「导出就出事」的修复：非流形边、配置无效、默认存到哪

用户拿去打印时一次性撞上三件事：3MF 存不下去、Bambu Studio 报错、模型颜色不对
且报了一万两千条非流形边。三件事的根因互不相干，逐个查。

### 31.1 默认目录：从隐藏的 `%LOCALAPPDATA%` 换到「下载」

`app/core/paths.py` 的 `exports_dir()` 原来返回 `data_dir() / "exports"`，也就是
`%LOCALAPPDATA%\BambuPalette\exports`——一个隐藏目录，而 Windows 的「受控文件夹
访问」还把这个位置判成没有写权限，于是保存对话框弹的是系统那句「你没有权限在此
位置中保存文件」。现在按顺序试 `%USERPROFILE%\Downloads`、`~/Downloads`，第一个
既存在又能真正写入（`_write_probe`）的胜出，都不行才退回原来的私有目录。

### 31.2 非流形边：底板曾经是「一块底 + 每种颜色一块，叠起来」

老的 `build_plate` 是两层实心堆叠：底板从 z=0 到 0.8，每种颜色再从 0.8 到 1.4。
颜色体块的**下表面**正好压在底板上表面上，侧面彼此也贴着——那是一片重合面、
内部墙的海洋。实测（`_meshcheck.py`，6×4 的玩具图，L 形那一块）：

| 网格 | 开放边 | 非流形边 |
| --- | --- | --- |
| 单个矩形色块 | 0 | 0 |
| **L 形色块** | **22** | **33**（其中 16 条正好 4 个面） |
| 拼接后（3MF 实际内容） | 22 | 33 |
| 全局焊接后 | 14 | 59 |

同时还有第二个 bug：T 型接点缝合时是「从 `polygon[0]` 扇形扇出去」，
`for k in range(1, len(polygon) - 1)`，会生成零面积三角形；第三个是整数化时
`np.rint(welded)` 把 z=0.8 和 z=1.4 **一起变成整数 1**，于是上表面的边拿到了
下面一层的顶点，缝出来的环根本不共面（`[(3,4,1.4),(2,4,1.4),(2,3,1.4),(2,3,0.8),(2,2,1.4)]`
这种环，任何三角化都缝不上）。

现在的 `app/mesh/plate.py` 是**一个真正的水密体**：

- 整个轮廓在 z=0 的下表面（底色）；
- 上表面在 `base_thickness + colour_thickness`，按区域铺，每个矩形带自己的挤出机号；
- 外侧立墙在 `base_thickness` 处**一分为二**：下段底色、上段是相邻区域的颜色；
- **没有内部墙**；部件是最后从这个整体里按面标签切出来的。

整数化改成 `_SCALE = 1_000_000`，扇形改成 ear clipping（只剪真正的耳朵：
`_cross2(a,b,c) > _EPS` 且三角形里没有别的顶点，共线的顶点永远不剪，因为它们正是
T 型接点要缝的目标），只在卡住时才退回老的扇形。

实测：玩具图 **0 开放边 / 0 非流形边**，体积 3080.0 = 22 像素 × 100 mm² × 1.4 mm，
`fan: 0`；示例底板从 **9,164 个三角面降到 2,012 个**，同样 0 / 0。
用户那张 512×512 的图原来是「发现 9,321 个开放边 / 错误 12,622 非流形边」。

### 31.3 配置无效：那份 `project_settings.config` 才是罪魁

`Plater::load_files` 会把工程配置交给 `check_project_config`，判定失败就整份丢掉，
并弹「3mf文件配置无效，仅加载几何数据」（zh_CN 里这条和
「该3mf文件不是来自Bambu Lab，将只加载几何数据」是**两条不同的字符串**，所以从弹
的是哪一条就能反推走了哪个分支）。配置被丢掉之后，Bambu Studio 就用**它自己的
耗材列表**去涂模型——这就是「颜色不对」的另一半原因。

用 GUI 逐个实测（写完文件→启动 Bambu Studio→截图→按回车关掉弹窗→再截图），
02.08.02.61 上的结果：

| 文件里的 `project_settings.config` | 弹窗 | 颜色 |
| --- | --- | --- |
| 26 键（当时发货的版本） | 「配置无效」 | 错（Bambu 自己的耗材） |
| 10 键（只有耗材列表） | 「配置无效」 | 错 |
| `nozzle_diameter` 与 `extruder_type` 等长 | 「配置无效」 | 错 |
| 去掉 `extruder_type` | 「配置无效」 | 错 |
| `{}`（空配置） | 无 | **对** |
| 干脆不写这个文件 | 无 | **对** |

结论：**任何「部分配置」它都不认**，而一个完整的配置是 555 个键、只有 Bambu Studio
自己写得出来。所以现在的做法是**不写 `Metadata/project_settings.config`**，让它走
标准 3MF 那条路——`The 3mf is not from Bambu Lab, load geometry data and color data
only.`——颜色从 `<basematerials>` 和 `paint_color` 里来，底板打开就是对的，而且
**什么弹窗都没有**。用户少的只是「Bambu 里那份耗材名字」，颜色、几何、逐面色编码
全都在，名字也仍然写在 `<basematerials name="…">` 里。

顺带记一条岔路：另一个办法是**冒充 Bambu Studio**（`Application = BambuStudio-…`），

## 32. 「非流形边」的真身是重复顶点，以及「配置无效」到底是什么

1.6.5 发布后用户又报了一轮，四项：默认保存地址、Bambu 报错、非流形边**且颜色错误**、
删掉双击混色。第 2 项这一版**没有修**，但查清了它是什么——31.3 的结论是错的，这里更正。

### 32.1 同一个位置存了两份顶点

用户那份导出的 3MF：**16,408 个顶点，实际只有 8,927 个不同位置**。多出来的 7,481 个是
各块自己的边界角点——每一块（底板、每个色块的上表面）各存一份，于是**每一条块与块之间
的边都属于两个不同的索引对**。

怎么数，决定结论：

| 数法 | 开放边 | 非流形边 |
| --- | --- | --- |
| 按**顶点索引**数（Bambu Studio 的数法） | **14,650** | 0 |
| 按**坐标焊接后**数（我们以前的数法） | 0 | 0 |

14,650 —— 和 Bambu Studio 报的数字**一模一样**。几何是闭合的，索引不是。

原因在两处：`app/mesh/threemf.py::_merged_mesh` 把每块的顶点表**首尾相接**，索引整体
偏移；`app/mesh/plate.py::edge_health` 数之前先按坐标焊接。**那个焊接正是把缺陷盖住的
东西**——这也是为什么 1.6.5 那轮「L 形 22 → 0」的量法看着是对的，发出去还是被报错。

### 32.2 为什么扫参永远测不出来

之前用 `_sweep.py` 扫过 27 组（8 原色库 / 5 卷大简库 × 三张图 × `max_colours`
2/3/4/6/8/10/12/16/24），**每组都是 0 开放边**——因为它量的也是焊接后的数字。输入怎么换
都碰不到这个 bug，只有换成按索引数才现形。

修法：合并只留一份实现 `app/mesh/plate.py::merge_parts(parts)`，以
`(round(x * _SCALE), round(y * _SCALE), round(z * _SCALE))`、`_SCALE = 1_000_000` 为键
（就是这个建模器自己的格点，而 3MF 写出的六位小数文本正好复现它，两种焊接必然一致）。
`plate_mesh`、`objfile.write_obj`、`threemf._merged_mesh` 都走它；OBJ 的 `_fmt` 也从
4 位小数改成 **6 位**，好让两边的顶点数对得上。`edge_health(points, faces, *, weld=False)`
默认**按索引**数，docstring 里写明焊接「是 1.6.5 那个缺陷藏起来的原因」。
`PlateModel` 多了 `shared_vertex_count`（合并后、也就是读文件的人会数到的那个数）。

修完按索引数：`_rt/toy.3mf` 1,008 顶点 **0/0**、`_rt/user-pig-12.3mf` 7,911 顶点
**0/0**、重新生成的 `samples/sample-plate.3mf` **0/0**；用户那份仍是 **14,650/0**。

**颜色错误大概率也是它**：半坏的实心体在外壳上会渲染发暗。用户截图里那只猪是暗的，
不是配色不对——每个面的颜色是逐三角面的 `paint_color`，跟顶点重复无关。

### 32.3 「保存地址还是隐藏目录」

`app/core/paths.py::exports_dir()` 1.6.5 时是**先探测再返回**。在打包好的 exe 里那次
探测失败了（它的数据目录是 `<app>\data`），于是退回 `<app>\data\exports`——正是截图上面
包屑显示的 `BambuPalette > data > exports`。现在**不探测**了：按
`_downloads_candidates()`（先是 `%USERPROFILE%\Downloads`，再是 `Path.home()/"Downloads"`）
返回第一个存在的目录，真写不进去才在写入处兜底
（`app/ui/picture_page.py::_write_model` 捕获 `OSError`，改存自己数据目录或主目录，
并弹出「已存到别的位置」告诉用户文件到底在哪）。

**为什么探测是错的**：探测回答的是「我们这个进程能不能在这里建文件」，而用户问的是
「我想在哪儿找到它」。这两个问题不一样。

### 32.4 「3mf文件配置无效，仅加载几何数据」到底是什么

先把那句话挖出来。Bambu Studio 的日志是加密压缩的，没用；`BambuStudio.mo`（zh_CN，
5,556 条）里第 **4436** 条 `msgid = 'The 3mf file has invalid config, load geometry
data only'`。旁边 4441/4442/4443 是另外**三条不同的**字符串，所以看弹的是哪一句就知道走
的哪个分支——我们遇到的是 4436。

然后做对照。拿一个**真正的** Bambu 工程（`Downloads\2-有ams_多色版.3mf`，571 键配置）：

| 文件 | 配置 | 结果 |
| --- | --- | --- |
| 原文件 | 有 | 干净打开 |
| 削掉缩略图/切片信息，**留**配置 | 有 | **干净打开** |
| 同上，**删**配置 | 无 | 弹框 |
| 我们的模型 + 借来的配置 | 有（571 键） | **弹框** |
| 我们的模型 + 借来的配置 + 缩略图 + `_rels` + 按 5 卷料改长的数组 | 有 | **弹框** |
| 我们的模型，加/减各种标记（`X-BBL-Client-Type`、`Application`、`3mfVersion`、`Metadata/` 整个删掉） | 无 | 弹框 |
| **手写的一个普通立方体**（无 Metadata、无 basematerials、无 paint_color） | 无 | **弹框** |

最后一行是决定性的：一个跟本程序毫无关系的立方体也弹同一个框。**结论：只要包里没有一份
完整的 Bambu 工程配置，Bambu Studio 就弹它**——这是它对第三方 3MF 的通告，不是我们的
文件坏了。借来的配置也压不住（它能被读进去，工艺预设确实换成了
`0.20mm Standard @BBL X1C`，框照弹），因为真正的判据是「这份配置是不是本机 Bambu 自己
写的那份」。冒充 Bambu 那条路 31.3 已经证明不可行。

**所以这一版不修它，也不该「修」它。** 代价是什么，说清楚：它只影响**打印设置**（工艺、
机器预设），不影响颜色——颜色是几何里的 `paint_color`，「仅加载几何数据」照样读。用户
自己报的那张截图就能证明：框在屏幕上，后面的板子是好几种颜色。要换预设，在 Bambu
Studio 里点一下就行。

### 32.5 删除双击「只看这一对耗材」

`app/ui/main_window.py` 里那行提示文字和 `_on_grid_activated` 一起删掉了，
`recipeActivated` 现在接到 `_on_grid_selected`（和单击同一条路），双击格子不再把颜色
网格收窄成一对。`_show_pair` 保留，只有详情面板那个
「只看这一对耗材的全部混色」按钮还能到达。`selftest` 和 `smoke_app` 各加了一条断言：
**双击一个两色混色不再设置 `_pair_filter`**。

### 32.6 这轮的验收

`Ran 289 tests … OK`、`tools/smoke_app.py` **371 项** `SMOKE OK`、`app --selftest`
`SELFTEST OK`、`tools/verify_bambu_roundtrip.py` `BAMBU ROUND TRIP OK`
（490 顶点 / 976 三角面 / **0 开放边 / 0 非流形边**）。

**一条经验**：一个「测量工具」如果先把数据规范化再测量，它就再也测不出规范化那一步

## 33. 「配置无效」的真正开关是 `Application`：一次被污染的实验教我的事

第 32.4 节当时下的结论是「这句话是 Bambu Studio 对任何第三方 3MF 的通用通告，
消不掉，跟本程序无关」。用户不接受这个答案，回了一句：

> 修理Bambu 报「配置无效」这个问题，参考blender的3MF Import/Export插件

他是对的。第 32 节那句结论建立在**被污染的实验**上。

### 33.1 先修测量工具：一次只开一个文件

之前的 `_gui_matrix.ps1` 一次跑好几个文件、共用同一个 Bambu Studio 进程，而且从来没有
可靠地关掉那个模态弹窗——**上一个文件留下的对话框会出现在下一个文件的截图里**。所以
「随便怎么改都弹」这个结论本身不可信。

换成 `_gui_probe.ps1`：每个文件**单独起一个进程**，跑完就杀；不截整屏，而是枚举该进程
**每一个可见的顶层窗口**，用 `PrintWindow(hwnd, hdc, 2)` 单独抓下来。

这样「弹了什么」就变成了可以按尺寸读的硬指标：

| 窗口尺寸 | 是什么 |
| --- | --- |
| **370×162** | 「3mf文件配置无效，仅加载几何数据」 |
| **792×207** | 「此配置可能由新版本的 Bambu Studio 生成。部分数值已被替换…」（配置**被接受**了） |
| **574×163** | 「自定义的预设 …请确认这些预设中的 G-codes 是否安全」 |

正对照：用户自己那份**真的** Bambu 工程 `2-有ams_多色版.3mf` 打开后**只有一个窗口**
（1549×925 主窗口），没有任何弹窗。

### 33.2 二分：把他们的文件和我们的文件逐块对调

模板配置（blender 插件那份）放进**他们的**容器 → 接受；放进**我们的**容器 → 无效。
于是把两边的零件一块一块换过去：

| 换掉的东西 | 结果 |
| --- | --- |
| 我们的 `model_settings.config` / `slice_info.config` / `filament_sequence.json` | **接受** → 元数据无罪 |
| 把我们的 `<mesh>` 塞进他们的 `object_14.model` | **接受** → 几何、`paint_color` 无罪 |
| 加 `<assemble>`、改成 Orca 的容器布局、删掉 `<basematerials>` | 无效 → 都不是原因 |

剩下的差别只有一处：`3D/3dmodel.model` 里的 `<metadata name="Application">`。

- 我们的 `BambuPalette` → **无效**
- `BambuStudio-BambuPalette-1.6.7` → **无效**（破折号后面必须是版本号）
- `BambuStudio-2.3.0` → **接受**
- `BambuStudio-02.07.01.62` → **接受**

blender 插件的 `export_3mf/orca.py` 里就写着这件事：

```python
# Use BambuStudio application name so Bambu Studio recognizes the file
# as a full project (not just geometry). Orca Slicer does the same.
# All rights reserved to Bambu Lab for the application name
meta_app.text = "BambuStudio-2.3.0"
```

**所以真正的机制是**：Bambu Studio 只有认出 `Application` 里的客户端标记，才会去读
`Metadata/project_settings.config`。认不出，它就把配置**整份丢掉**，然后说「配置无效，
只加载几何数据」——**顺便也用不了配置里的配色**。这就是用户看到的「颜色也错了」。

### 33.3 配置还必须是完整的，而且不能是「自定义预设」

光有标记不够，配置本身也有限制（同样是一个文件一个进程测出来的）：

| 包里的配置 | 结果 |
| --- | --- |
| 5 个键 | 370×162 **无效** |
| 15 个键 + `filament_settings_id` | 574×163（接受，但被当成**自定义预设**） |
| 12 个键、不含 preset id | 574×163（同样警告，预设名是空的 `-`） |
| blender 那份 511 键模板 + 我们的配色 | **接受** |

第三条说明了警告的触发条件：**只要配置里点名的 preset 在那台机器上不存在**，Bambu
Studio 就认为这份配置带着自定义 G-code，要用户确认。blender 模板之所以不触发，是因为
它点的是 `Bambu Lab A1 0.4 nozzle`、`Generic PETG @BBL A1`、`0.20mm Standard @BBL A1`
——这几条是**每台机器都装的出厂预设**。

还有一个小坑：模板里 `ensure_vertical_shell_thickness = "ensure_all"`（Orca 的写法），
Bambu Studio 会替换成 `"enabled"` 并**为此再弹一个「部分数值已被替换」的窗**。改写成
Bambu 的拼法之后，弹窗归零。

### 33.4 改法

`app/mesh/threemf.py`：

- `THREEMF_APPLICATION = "BambuStudio-2.3.0"`（来源与理由写在常量上方的注释里）；
- 打包 `app/mesh/orca_project_template.json`（511 键，来自 blender 插件，GPL-3.0-or-later，
  与本程序同许可，`NOTICE.md` 第 8 节有署名），`_project_settings()` 只改与耗材有关的部分：
  `filament_colour` 换成配色，`filament_*` 与另外 17 个「每个耗材一项」的数组按耗材数补齐/
  截断（照 `export_3mf/orca.py::generate_project_settings()`），再把
  `ensure_vertical_shell_thickness` 换成 Bambu 的拼法；
- `Metadata/project_settings.config` 重新写进包里（1.6.5、1.6.6 是**故意不写**的）；
- `Metadata/slice_info.config` 里的 `X-BBL-Client-Type` 仍然是 `BambuPalette`：兼容性标记
  只在 `Application` 那一处，写出程序是谁还是照实写。

## 34. 1.6.8：下载写不进去的真身是目录上的 Low 完整性标签；外加滚轮缩放

### 34.1 两条失败消息，一个原因

用户报了两件事（截图）：

> 导出失败 / cannot write library to C:\Users\xzz\Downloads\Bambu Lab 41色 耗材档案.json: Permission denied

> 保存3MF 模型 / C:\Users\xzz\Downloads\猪包_20261011-163337.3mf / 你没有权限在此位置中保存文件。请与管理员联系以获得相应权限。你想改为保存到 xzz 文件夹中吗？

一条是本程序自己的报错（`FilamentLibrary.save()` 写临时文件时 `EACCES`），一条是
Windows 保存对话框自己的报错。两条指着同一个目录，而且都发生在**用户亲手启动的**
exe 上。

排查过程（下面这些都不是原因）：

| 怀疑 | 实测 |
| --- | --- |
| 文件只读 | `IsReadOnly: False`，`Attributes: Archive` |
| 目录 DACL 不给写 | 继承的 `DESKTOP-4CBHGJ5\xzz:(F)` 在，从提权 shell 里 `AppendAllText` 成功 |
| 勒索软件防护 | `EnableControlledFolderAccess = 0`，保护目录为空 |
| 杀软拦 | 只有 Defender，没有 ASR 规则 |
| 沙箱组的只读 ACE | `CodexSandboxUsers:(OI)(CI)(RX)` 确实在，但 ACL 里的 allow 只会**加**权限，不会减 |

把「同样由资源管理器启动」的两个程序放在一起比，才出现分水岭：

* `cmd.exe`（Medium）能在下载目录里建文件、复制文件；
* **`python.exe`（同一个解释器）不能**，任何名字都 `errno=13 Permission denied`。

同一个用户、同一个目录，区别只剩下进程的**完整性级别**（integrity level）。

### 34.2 `Get-Acl` 看不见的东西

第一次用 PowerShell 读完整性标签，读到的全是「没有标签」：

```powershell
(Get-Acl $path).Sddl      # S:AI —— 空的
```

**这是错的。** .NET 的 `GetSecurityDescriptorSddlForm()` 会把强制标签（mandatory label）
那一条 ACE **悄悄过滤掉**，于是「读不出来」被当成了「不存在」。换成 `icacls` 就一眼看见：

```
C:\Users\xzz\Desktop\dc works    Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)
```

`dc works` 上这一条是**显式**的（没有 `(I)`），下面每一层都继承它：工程目录、
`.venv\Scripts`、`dist`，一直到用户手里那个 `BambuPalette.exe`——光是
`...\dist\BambuPalette-1.6.7-win64\BambuPalette\` 一个目录里就有 269 个带 Low 标签的对象。
而 `C:\Users\xzz\Desktop` 本身没有标签。

机制是 Windows 的强制完整性控制：**映像文件带 Low 标签，进程就以 Low 启动**；Low 进程
对普通（Medium）对象没有写权限，哪怕 DACL 明明白白写着 `FullControl`。于是：

* `open(f"{target.name}.{os.getpid()}.{attempt}.tmp", "x")` → `EACCES` → 「Permission denied」；
* 保存对话框 → 「你没有权限在此位置中保存文件」。

实测（P/Invoke 读 `TokenIntegrityLevel`，0x1000 Low / 0x2000 Medium / 0x3000 High）：

| 程序 | 怎么启动的 | 完整性级别 |
| --- | --- | --- |
| `explorer.exe` | — | `0x2000 Medium` |
| `cmd.exe` | 资源管理器 | `0x2000 Medium` |
| **`BambuPalette.exe`** | 资源管理器（双击） | **`0x1000 Low`** |

### 34.3 修法

```powershell
icacls "C:\Users\xzz\Desktop\dc works" /setintegritylevel Medium /T /C /Q
```

之后同一个 exe 再双击，进程是 `0x2000 Medium`，`.venv` 里的 `python.exe` 也是；用
`FilamentLibrary.save()` 往 `C:\Users\xzz\Downloads` 写文件、`os.replace`、再删除，
全部成功。

这不是程序的 bug：**zip 里不带完整性标签**，换一个普通目录解压出来的副本不会有这个
问题，它只发生在「解压到被打过 Low 标签的目录里」这一种情况。README「已知限制」里
记了症状和这一行修法，下次再遇到可以照抄。

### 34.4 「原图 / 预览」加了滚轮缩放和拖动平移

用户的第二件要求：

> 原图和预览添加功能，通过滚轮键实现放大和缩小，图片可以在窗口内平移

`PictureView` 原来的 `_target_rect()` 是**纯铺满**：每次调用都把 `_scale` 重算成
`min(可用宽/图宽, 可用高/图高)`，`_origin` 永远居中。缩放平移叠在它之上，拆成三个量：

```python
self._fit_scale = min(available_w / width, available_h / height)   # 铺满的基准
self._scale = self._fit_scale * self._zoom                          # 画多大
self._origin = (widget - draw) / 2 + self._pan                      # 画在哪
```

这样改窗口大小时基准会重算，用户放大的倍数不会被算丢。

* **滚轮**：一格乘 `ZOOM_STEP = 1.25`（高分辨率滚轮的小数格用指数形式一并处理），夹在
  `ZOOM_MIN = 1.0`（铺满）到 `ZOOM_MAX = 12.0` 之间；
* **对着光标缩放**：先记下光标处的图像坐标，改完倍数再反解 `_pan`，让那个像素**停在
  光标底下**，而不是把画面往中间拽；
* **拖动平移**：`_clamped_pan()` 把位移夹在 `±(draw - widget) / 2`，画面永远不会被拖出
  面板露出空缺；没放大时余量是 0，也就是永远居中；
* **左键既要挑颜色又要平移**：按下时只记起点，松手时按移动距离判断——超过
  `DRAG_SLOP = 3` 像素算平移（不挑颜色，因为画面动过了），否则算点选，走原来的
  `result.indices[y, x]`；
* **双击还原**：回到「整张铺满」并清掉平移，顺手丢掉这次按下的状态，免得松手时又被
  当成一次点选。

两个面板都套用（「原图」是素模式，照样能缩放平移），提示语写在面板、视口和标题三处。
`selftest` 新增 14 项：起始 1×、两格到 1.562×、放大后画面确实比面板大、光标下的像素
不跑、上限 12×、拖动不误选、拖动确实移动了、位移被夹住、两边都有提示、复位回 1× 且
`_pan` 归零、普通点选仍然挑中光标下那个像素。

### 35.1 隐藏耗材：一个布尔值，和它必须一次性传到的地方

「料用完了还没买回来」是耗材库里很常见的一种状态：它既不该被删（颜色还要留着，
买回来接着用），也不该继续参与计算。所以 `Filament` 多了一个 `hidden`：

```python
@dataclass
class Filament:
    hidden: bool = False
```

三条约束，决定了实现长什么样：

1. **行还在表里**。用户得看得见它才能在想用的时候放回来，所以列表照样列出这一行，
   只是变灰（`theme.TEXT_FAINT`）并在名字后面标「（已隐藏）」；右键菜单按当前状态
   给「隐藏」或「取消隐藏」。
2. **只写一个字节**。`to_dict()` 先照旧拼出原来那份 `data`，**只在 hidden 为真时**
   才加 `data["hidden"] = True`：

   ```python
   if self.hidden:
       data["hidden"] = True
   ```

   于是没隐藏过任何耗材的档案，序列化结果与 1.6.8 一个字节都不差——老档案、
   和别人共用的档案都不受影响。
3. **过滤只做一次**。最省事的写法是在匹配器、网格、「全部颜色」、导出这四处各自
   `if filament.hidden: continue`，但那四处迟早会走岔。程序加的是：

   ```python
   @property
   def visible(self) -> list[Filament]:
       return [filament for filament in self._filaments if not filament.hidden]
   ```

   然后让**所有配方表都从 `library.visible` 建起来**（`MixCatalog(...)`、
   `catalog.sync(...)`、`TripleCatalog(...)`、`CombinedColours(...)`、三色缓存键
   `triple_cache_key(...)`、搜索掩码）。藏一卷料在语义上就等于**换了一个耗材库**，
   于是三色混色那张跟着清单走的缓存表由 `_invalidate_triples` 丢掉、`_ensure_triples`
   按新键重找——藏一卷料后第一次打开要等的那几分钟，就是在这里花掉的。

   `has_any = len(self.library) > 0`（列表里还有没有行）和行循环**故意**用完整库，
   不能用 `visible`：只剩隐藏耗材时列表也得是「非空」，否则界面会退回空库引导。

### 35.2 32 是 Bambu Studio 的天花板，`CONST_FILAMENTS` 不是那条线

用户想把「颜色数量」的上限从 32 提上去。查下去发现这不是本程序的限制，而且**第一直觉
是错的**。把 BambuStudio v02.08.02.61 和 OrcaSlicer v2.4.2 的源码摊开读，结论如下。

先看那个最像答案的东西——`src/libslic3r/Model.cpp:57`：

```cpp
const std::vector<std::string> CONST_FILAMENTS = {"", "4", "8", "0C", "1C", ... "EFC"};
```

33 条，正好够 1..32，看着就是那道天花板。**但它和 3MF 的 `paint_color` 毫无关系**：
全仓库只有三个引用——它自己的定义、`get_real_filament_id`
（`Model.cpp:4119-4126`，越界时打 `check error:CONST_FILAMENTS out of array` 并返回 `""`）、
以及**只被 OBJ 彩色网格导入**调用的那两个函数（`Model.cpp:4220-4267`、`:4299`）。

真正的编码在 `TriangleSelector::serialize`（`src/libslic3r/TriangleSelector.cpp:1997-2056`），
注释就写在函数头上：

```cpp
// leaf triangle: xx = 0b11, yy = 0b00, zzzz = EnforcerBlockerType (subtracted by 3)
```

> 三种耗材以上：先压 `{true,true}`，然后 `while (n >= 15) { 压 4 位; n -= 15; }`，最后压
> `n` 的 4 位。

读的那一半（`TriangleSelector.cpp:2111-2152`）镜像它，而且**不设上限**：

```cpp
while (next_code == 0b1111) { num++; ... }
state = EnforcerBlockerType(next_code + 15 * num + 3);
```

也就是说**线格式本身没有 32 这道线**（状态 20 就是 `0xC, 0xF, 0x2`）。

线在哪里？在**枚举**上：

```cpp
enum class EnforcerBlockerType : int8_t {
    NONE = 0, ENFORCER = 1, BLOCKER = 2, FUZZY_SKIN = ENFORCER, Extruder1 = ENFORCER,
    Extruder2 = BLOCKER, Extruder3, ... Extruder32, ExtruderMax = Extruder32,
};
```

（`src/libslic3r/Model.hpp:716-756`）运行时上限由工程耗材数决定：
`ModelVolume::update_extruder_count(size_t)`（`Model.cpp:3417-3425`）→
`set_enforcer_block_type_limit(..., (EnforcerBlockerType)extruder_count)` →
`selector.deserialize(m_data, false, max_type, ...)`（`Model.cpp:4566-4567`）。
超出的部分撞上 `TriangleSelector.cpp:2149-2152`：

```cpp
if (state > max_ebt) { assert(false); state = EnforcerBlockerType::NONE; }
```

**release 版本里这是静默的**：第 33 种颜色不会被拒绝，而是被当成「没涂色」，
跟着对象 / 全局耗材打出来。debug 版本会 assert。工程耗材数自身也被夹住：
`PresetBundle::set_num_filaments`（`src/libslic3r/PresetBundle.cpp:2365-2368`）里
`if (n > (unsigned int)(EnforcerBlockerType::ExtruderMax)) n = ...`，
另有 `Plater.cpp:4152`、`:5163` 两处同样的夹取。配置项本身不限长
（`filament_colour` 在 `PrintConfig.cpp:2393`），所以手改一份 40 条耗材的
`Metadata/project_settings.xml` 也能载入——**但界面会夹回 32，第 33 条起永远画不上色**。

OrcaSlicer **更严**：它的枚举到 `Extruder16` 就停了（`TriangleSelector.hpp:13-38`），
写入侧 `assert(n <= 16); if (n <= 16) { ... }` 且**没有 15 的续位**
（`TriangleSelector.cpp:1738-1746`），读入侧只多读一个 nibble（`:1822`），
超过 16 的一律清零（`:1831-1834`）。它的工程列表允许 64
（`MAXIMUM_EXTRUDER_NUMBER = 64`，`libslic3r.h:65`），但画笔仍然只到 16
（`GLGizmoMmuSegmentation.cpp:742`）。**所以在本程序里用第 17–32 号槽画出来的颜色，
导进 Orca 会丢**。

用户看完给了决定：

> 我刚刚跟人工客服提交工单了，未来的版本拓竹会修好这个bug，暂时先按32

于是 32 保持不变，只把**原因**写进界面悬停提示和 README——上限不解释，用户只会以为
是程序偷懒。

顺带记一个容易搞混的单位：一份调色板里**一个颜色 = 一个耗材位**。
`app/mesh/threemf.py:347 slots_from_palette()` 给每个调色板条目建**一个** `FilamentSlot`，
`:379 _project_filaments()` 按 `part.extruder - 1` 取它。所以
`MAX_PAINTED_FILAMENTS = 32` 限的是**颜色数**，不是耗材卷数——一卷料可以混出很多颜色。

### 35.3 三色进候选：不枚举，反向查

第一页早就会算三色混色（第 23 节），但它一直没进图片匹配的候选池，原因只有一个：
数量级。41 卷料是 C(41,3) = 10,660 组 × 2,556 个配比 = **2,724 万**条配方，
逐条造成对象是不可能的。

反过来做就成立了。新类 `TriplePalette` 把候选池拼成**两段**：

* **head**：本色 + 两两混色（41 卷时 66,461 条），照旧是对象，可以随便索引；
* **tail**：三色混色（400 多万个颜色），**只保留 `TripleCatalog.packed` 那个
  int32 数组**，一条对象都不建。

`__len__` 是两段之和，`__getitem__` 落在 tail 时**现做**那一条
`PaletteEntry`（`recipe=None`，改用一个新字段 `parts: tuple[tuple[str, int], ...]`
承载「哪几卷、各多少百分比」——三色配方没有 `MixRecipe` 可用）：

```python
parts = ((recipe.a_id, recipe.percent_a), (recipe.b_id, recipe.percent_b),
         (recipe.c_id, recipe.percent_c))
```

`ratio_text` / `short_label` 以及 `app/ui/colour_picker.py` 的两个格式化函数都加了
`entry.recipe is None and not entry.parts` 这个守卫，所以两色路径的输出与以前**逐字节
相同**，三色才落到新分支。

最近邻搜索也跟着分两段（`app/core/image_matching.py`）：

```python
def _shortlist_indices(table, targets, shortlist):   # 分块欧氏距离 + 每行 argpartition
    ...
```

`_nearest_entries` 对**完整** Lab 表跑一次 `_shortlist_indices`，**再**对
`table[:head_size]` 跑一次，两批候选合起来才进精确的 CIEDE2000 那一遍。
`head_size` 由 `TriplePalette.head_size` 提供。这一步不是优化，是**正确性**：
只有一次筛选时，一个宽得多的 tail 完全可能把一个更省料、同样接近的两色答案
挤出 24 条的候选名单——勾上「也算三色配方」反而把颜色变差，是这条功能唯一不能犯的错。

尾巴的 Lab 表不用重算，直接复用 `TripleCatalog.lab_table()` 已经缓存好的
`(C, 3) float64`，用 `np.isin(packed, taken, assume_unique=True)` 减掉被 head 覆盖的
那些颜色——**同色时 head 赢**，因为本色/两色更省换料。整表只有一份缓存，
`selftest` 专门盯着「建了一次，不是每次匹配建一次」。

### 35.4 「这次最多用几卷料」：预算在合并近似色之后才执行

`MatchSettings` 多一个 `max_spools: int = 0`（0 = 不限，`clamped()` 里夹到
`0..MAX_PAINTED_FILAMENTS`）。执行顺序很关键：

```
最近邻 → 按面积排序 → 合并肉眼分不出的近似色 → 预算 → 结果
```

**放在合并之后**是因为合并本身就会白送耗材：两个差 1 个 ΔE 的色阶被折成一个，
预算凭空多出一卷料的位置。

预算的算法是贪心（`_fit_spool_budget`）：按面积从大到小走，手里已有的卷不算钱，
新颜色要么「它的料我都有」，要么「加上它总卷数不超预算」；否则**退而求其次**，
用 `delta_e_2000` 在已经收下的条目里找最近的一个顶替。第一条颜色无论如何都保留——
预算比一份配方还小是用户自己给的矛盾条件，为它把整张图重画一遍不合理。

两个在这里踩到的坑：

* **`_renumber` 数错了人**。它原来按 `range(len(kept))` 重新编号，于是**一个像素都没用
  到的条目也会活着**被返回——一卷料可能因此被带进底板槽位表，正是预算承诺不会发生的事。
  改成只对 `np.unique(folded[folded >= 0])` 里真实出现过的值计数、排序、重编号。
* **`remap` 存的是 `accepted` 里的位置，不是 `pool` 里的下标**。于是
  `_renumber(pool, folded)` 取回了错误的条目（预算 1 却能留下一条两卷料的两色配方）。
  改成 `_renumber([pool[position] for position in accepted], folded)`。

还有一条**看起来像 bug、其实是探测脚本自己错**的：取消隐藏后 `hidden` 还是 `True`。
原因是 `FilamentLibrary.update()` **替换**了存储的对象，脚本手里的旧引用 `hidden` 仍是
`False`，而 `_set_hidden` 开头就是

```python
if filament.hidden == hidden:
    return
```

界面本身没问题：菜单通过 `_selected_filament()`（`app/ui/main_window.py:533-537`）
每次都用 `self.library.get(item.data(Qt.ItemDataRole.UserRole))` **重新读活的对象**，
所以它给出的动作永远是对的。脚本重新取一次对象，取消隐藏立刻正常。

## 36. 1.6.10：把「要不要」的问题删掉，让不该转的圈停下来

> 1、不要预设颜色。2、文本更改：'混色耗材色彩管理器 · 每两种耗材 81 个配比'改成
> '混色耗材色彩管理器 · 每两种耗材 81 个混色，每三种耗材 2556 个混色'。3、文本错误，
> 导入文件中包含了混色，却提示说还在计算，而且我的鼠标一直在转圈。4、删除悬停黑窗
> 功能。5、删除☑ 混色也算候选☑ 也算三色配方和悬停黑窗，全部颜色参与匹配。6、颜色
> 数量默认32，耗材上线默认为4。7、添加耗材名称删除文本'可选，例如「大筒 PETG HF 金色」'

### 36.1 两个勾选框都不是真选择

`混色也算候选` 和 `也算三色配方` 描述的是**候选池的大小**，而「小一点的候选池」
在这里不是更省的答案，是**半个答案**：41 卷料的混色 66,420 条、三色 400 多万条，
全都是「你图片里的颜色可以由这几十卷料调出来」这一条知识。关掉它，匹配照样跑完，
只是颜色更差——用户看不出这是自己关掉的，只会觉得程序配得不准。三色尤其没有
讨论的余地：第一页早就把那张表算好并缓存了（§23），摆在那里不用，只是让用户
替一个已经付过的成本再签一次字。

真正需要人决定的只有两件**机器事实**，不是审美偏好：这台机器**一个工程放得下
几个颜色**（32，Bambu Studio 自己的天花板，来龙去脉见 §35.2），和**这次打印
最多用几卷料**。这两条留在工具栏上，两个布尔值删掉。删完 `_candidate_palette()`
只剩「建过没有」一个判断，缓存键里那个「勾选框状态」自然也没了（§18.2）。
三色表算完之前，这一页先拿本色 + 两色匹配，算完自动接上——不必等，也不必点。

### 36.2 默认值取机器事实：32 与 4

`颜色数量` 默认从 12 改成 **32**，`耗材上限` 默认 **4**。32 就是天花板本身
（用户要的是「别让我每次手动顶到上限」，而系统上限不该比机器上限小）；4 是
一台常见 Bambu 机器的四卷 AMS。默认值在这里是有意义的：它们决定第一次点
「重新匹配」看到的图是什么样子。

### 36.3 空对话框不该等于黑色

`_resolved_hex()` 原来是

```python
return self._color.hex() or self._color.rgb_to_hex(self._color.rgb())
```

——「用户什么都没填」被这个 `or` 翻译成 `#000000`，三只数字框显示 `0, 0, 0`，
下面那行提示还主动告诉你「什么都没填就按三个数字框里的值算，现在是 RGB 0, 0, 0」。
于是**手滑点一下「确认」就多一卷黑色的料**。三处一起改：兜底删掉（没填就是没填）、
提示改成「请填写颜色：可以直接输入 #RRGGBB，也可以填 R / G / B 三个数字。」、
`确认` 和 `下一个` 在没填颜色时置灰。

**坑：`QSpinBox` 没有「空」这个状态。** 它装的是 `int`，`setValue(None)` 不存在，
`setSpecialValueText()` 是 Qt 给的唯一办法——它给**最小值**配一段替代文字。把 0
显示成一个空格，数字框看起来就是空的，而真实值仍然是 0：用户一碰箭头或者一敲
键盘，`_on_spin` → `_set(QColor(r, g, b))` 就会把它变回正常显示。反过来，
**纯黑 `#000000` 的通道值也是 0**，会被同一招吃掉成空白，所以设置顺序有讲究：

* 填色时 `spin.setSpecialValueText("0")` 必须在 `spin.setValue(channel)` **之前**；
* 清空时 `spin.setSpecialValueText(" ")` 也要在 `spin.setValue(0)` **之前**。

顺序反了，`#000000` 会显示成空白（看起来像没填）或者未填状态会显示成 `0`。

### 36.4 「正在计算三色混色」与下不来的光标

`_on_import()` 的顺序错了：

```python
self._reload_library()          # 这里面 _ensure_triples() 起了 QTimer + 等待光标
...
self._adopt_mix_sidecar(...)    # 现在才发现档案旁边就有现成的表
```

`self._triples` 被换成缓存表，但计时器还活着，而它每次 `step()` 都往**那张旧的、
已经被换掉的**表的 `_mixed` 数组里写——那张表连 `begin()` 都没走过，中间数组
根本不存在，进度于是永远停在 0；`_end_build_notice()` 是正常路径上
`_step_triple_build()` 的最后一件事，这条路走不到，等待光标再也不还原。用户看到的
就是「档案里明明带着混色，却提示还在计算，鼠标一直转圈」。

修法是把「这份档案自带缓存」变成一个**先于重建库的知识**：`self._pending_sidecar`
在 `_reload_library()` **之前**登记，`_ensure_triples()` 一看到它就返回（几毫秒后
缓存就换上了，现在开始算是白算），`_adopt_mix_sidecar()` 里补上
`_stop_triple_timer()` 和 `_end_build_notice()`；认不下来（表不是这套耗材的）就
清掉登记、走正常的 `_ensure_triples()`。

验收不是「看代码顺眼」：`tools/smoke_app.py` 现在**真的调一次
`MainWindow._on_import()`**（文件对话框和消息框都换成桩），断言导入后
`_triples.built`、`_triple_timer is None`、`_build_notice` 为假、
`QApplication.overrideCursor() is None`、状态栏里没有「正在计算三色混色」。
后面还有一条**阳性对照**：同一份档案、**旁边不放缓存**再导一次，这次必须真的起
计时器（`_triple_timer is not None`）。没有这条对照，上面五条断言在一个「导入
根本不开始算」的实现下也会全绿——阳性对照才是让这组测试有牙齿的那一条。

## 37. 1.6.11：先量再改的进度条、按耗材数的用量、以及「改到一半」存下来

六条反馈：三条是新功能（进度条、「用到的耗材」、工程文件），三条是做减法

> 1、不要预设颜色。2、图像转换和重新匹配的时候给个进度条。3，匹配完成后显示一下
> 用到了哪些耗材。4、修改文本，把更换颜色按钮后面的...删掉。5、添加功能，导出当前
> 已经被修改过的图片的文件，其中包括原图和预览图，这个模型需要的颜色，需要的耗材
> 颜色，方便用户下次打开继续修图，而不是从头开始修，ctrl+s保存文件。6、文件，视图，

### 37.1 进度条：先量，再决定改什么

用户要的是「有个进度条」，但**加一条进度条之前得先知道那些时间是花在哪一段**——
不然进度条只会把一段真实的沉默装成动画。`tools/probe_match_timing.py` 因此先写出来：
它按 `match_image(..., progress=...)` 每次回调打一个时间戳，于是每个阶段的真实耗时
直接就是相邻时间戳的差。测的是 1875×1188 的图、512 px 上限、32 色：

| 场景 | 总耗时 | 「寻找最接近」 | 「分配」 |
| --- | --- | --- | --- |
| 8 卷料 + 三色尾巴（93,832 色） | 1.87 s | **1.38 s** | 0.33 s |
| 41 卷料，只有本色 + 两色（49,943 色） | 1.66 s | **1.33 s** | 0.19 s |
| 41 卷料 + 三色尾巴（1,482,058 色） | 3.03 s | **1.38 s** | 1.47 s |

再看 `cProfile`（41 卷、只看本色 + 两色，总共 3.48 s）：

```
8734 calls  1.509s tottime  1.569s cumtime  app/spectral/color.py:489(delta_e_2000)
 405 calls  0.405s tottime                   app/core/mixes.py:481(_compute_pairs)
 117 calls  0.284s tottime                   app/core/image_matching.py:117(build_palette)
```

结论很清楚：**那 1.3–1.5 秒就是 8,734 次标量 CIEDE2000**（≈192 个减色后的颜色 ×
≈45 个入围候选，`reduce_colours` 本来就按 `_OVERSAMPLE = 6` 多留了几倍）。
`delta_e_2000` 向量化能把这 1.5 秒压到毫秒级，但那要动颜色科学那一层，
是**另一件事**：这一版只做「看得见」，把数字留在文档里，等有人说「还是慢」再动它。
这样处理的好处是：进度条的每一秒都对得上一个真实的计算，而不是让动画替算法道歉。

两个实现细节：

* **进度条先等 200 毫秒**（`BUSY_DELAY_MS`）。五卷料的小图半秒匹配完，让进度条闪一下
  比没有还烦；200 毫秒之后才显示，并且**显示时就已经按实际进度停在中间**，
  不会从 0 开始装样子。`_begin_match()` 起 `QTimer`，`_show_progress()` 才
  `setVisible(True)`，`_end_match()` 无论如何都收尾（成功、失败、被换掉都收）。
* **「重新匹配」在匹配期间是灰的**。界面照常重绘（`QApplication.processEvents()`），
  但入口关掉——不然一次点击就能叠第二次匹配，两套进度互相覆盖。

### 37.2 「用到的耗材」不是「这个模型需要的颜色」

用户要的是「匹配完成后显示用到了哪些耗材」。看起来像给左边的颜色清单加一列，
其实**不是同一个数**：一块「白 90% + 金 10%」的区域，耗的是 90% 的白和 10% 的金；
按颜色块数去数，那一块在白和金头上各算 1（看起来像各占一半）。所以另开一栏，
按**色料比例**摊：

```python
share = int(result.counts[index]) / printed        # 这一色占整张图的像素比
spend[str(filament_id)] += share * percent / 100.0  # 再按配方百分比摊到各卷
```

于是 `spool_usage(result, library)` 返回 `SpoolUse(filament_id, share, filament)`，
按份额从大到小排序。三条规矩：

* 一个混色会摊到两卷或三卷上，所以这一栏**本来就对不上颜色清单的行**——它不是清单的第二列；
* 比例是**质量占比**，所有行加起来 100%；删除 / 合并 / 更换颜色 / 撤销 / 恢复都会重算；
* 库里已经没有的那一卷**照实说**：「耗材库里已经没有这一卷」，颜色用工程文件里存的那个。
  界面可以少画一个色块，但不能编一个颜色出来。

（`spool_usage` 住在 `app/core/image_matching.py`，和 `MatchResult` 一起，
不是住在界面里——工程文件那一层也要用它，核心不能反过来 import 界面。）

### 37.3 工程文件：把「从头再修一遍」换成「接着改」

用户的原话是「方便用户下次打开继续修图，而不是从头开始修，ctrl+s保存文件」。
所以存的不是一张图，是**这一页的状态**。容器是一个 zip（`.bpproj`）：

| 成员 | 为什么是它 |
| --- | --- |
| `工程.json` | 编辑状态（删除 / 合并 / 更换颜色）、基线键、用的引擎、打印参数、用到的耗材 |
| `原图.png` | 用户导入的那张图本身——**图必须在文件里**，否则「发个工程」等于发个打不开的壳 |
| `预览.png` | 打开时看到的预览，也是这个文件「肉眼可查」的那一半 |
| `基线.npy` | 自动匹配的逐像素索引：有它才是「接着改」，没有它就只能重匹配一遍 |

几个必须做的决定：

* **打开时连工具栏设置一起恢复**（颜色数量 / 耗材上限 / 最大边长 / 抖动）。不恢复的话，
  用户按「重新匹配」得到的是一张**用当前窗口的设置算出来的**图，和他存下来的那张不一样
  ——那就不是「接着改」了。
* **有未保存改动时先问一句**（先保存 / 不保存 / 取消），默认按钮是「取消」。这条问得
  比什么都值：删除和合并是**不可逆的**编辑（撤销栈不跟着文件走）。
* **默认存在「下载」文件夹**，和导出的模型一样。工程文件是要拿去接着改、可能还要发给
  别人的东西，存在程序自己的数据目录里等于让人找不到（§31 那条「导出就出事」的同一条道理）。
* **工程里不含耗材库本身**。它在哪台机器上打开，就用那台机器的耗材库接着算；文件里记着
  用到的每一卷的名称 / 品牌 / 种类 / 颜色，跟着建就行。把库塞进工程反而会让「用谁的库」
  变成一个没人能回答的问题。
* 颜色键用的是**耗材 id**，不是颜色值：同一卷白料换个色号，用户的「更换颜色」不该跟着漂。

`project._live_palette` 和界面里的 `_compose` 用**同一条存活规则**
（`index not in gone and index not in merged`，合并链要跟到底，被删掉的颜色把合并到它
身上的颜色一起吃掉）：文件里存的编辑，重新算出来必须是用户存下来的那张图，差一个像素
都是 bug。

### 37.4 三个菜单删掉，一个「关于」留下

`menuBar` 整个移除。菜单里的动作**没有一个消失**，因为它们本来都有看得见的按钮：
添加耗材 → 右上角「添加耗材」；导入 / 导出耗材档案 → 「我的耗材」下面的「导入 / 导出」；
显示全部颜色（Ctrl+0）→ 颜色配方页右上角那个按钮；退出（Ctrl+Q）→ 窗口的关闭按钮。
唯一没有对应按钮的是「关于与算法来源」，所以给它**单独一个非强调色按钮**（版本号、
算法来源、许可说明都在那个窗口里）——删菜单不等于删掉出处。

`Ctrl+N / Ctrl+Q / Ctrl+0` 跟着菜单一起去掉：项目现在的规矩是**不放看不见的入口**

### 37.5 「清空耗材库」：先把文件在哪说清楚

「不要预设颜色」在 1.6.10 改掉的是「添加耗材」对话框那一半（§36.3）。另一半是
**用户库里那些从没打印过的料**：新建一份程序是空的（smoke 里那扇窗口构造出来就是 0 条），
但旧版本、样张脚本、或者一次误点的「导入」都会在库里留下十几卷料，而删掉它们原来只能
一卷一卷点「删除」。

* 按钮放在**卡片标题那一行**，不和下面的「编辑 / 删除 / 导入 / 导出」挤在一起——
  破坏性动作不该长在常用动作旁边；库里没料时它是灰的；
* 对话框里写清完整路径、写明**它不在程序目录里、也不跟着安装包走**（这台机器上所有副本
  共用这一份，所以「重新解压一份」不会让耗材消失）、写明不能撤销并建议先「导出」；
* 默认按钮是「取消」。

### 37.6 一个真崩溃：面板不能抓着已经被删掉的东西不放

清空耗材库时，如果右侧「颜色配方」正显示着某个混色，它的父项刚被删掉，
`showRecipe` 会给配色条传一个 `"?"`（父项不在时的占位符），而配色条要求 `#RRGGBB`：

```
ValueError: colour must be '#RRGGBB', got '?'
  app/spectral/color.py:160(hex_to_rgb) ← PairBar.setPair(hexes[0], hexes[1], …)
```

修法是给 `setPair` 一个判断（`_hex_ok()`）：色值不能用就**画成一条空槽**，不抛异常。
这和这一轮其它几处是同一个道理：**库变了，抓着旧状态的面板必须自己让路**，
不能让用户看见一个回溯。它是这一版唯一一个崩溃，而且是靠「清空」这条新路径走出来的——
新功能的价值之一就是**把老代码里没人走过的路走一遍**。

### 37.8 两条经验

1. **「加个进度条」是一个性能问题的问法。** 先量出 1.5 秒里有 1.509 秒是标量
   CIEDE2000，进度条才不会变成替算法道歉的动画；而量出来之后最该做的优化
   （向量化 `delta_e_2000`）**没有做**——它是独立的一件事，值得单独提出来，
   而不是夹在「加进度条」里悄悄改掉颜色科学那一层。
2. **新功能会把老代码里没人走过的路走一遍。** 这一版的崩溃（37.6）不是新代码写错的，
   是「清空耗材库」让「详情面板正显示一个刚被删掉的混色」第一次真的发生了。
   写新入口的时候顺手想一想：**它会让哪个面板抓着一个已经不成立的状态**。

### 37.9 数据目录：从「这台机器一份」改成「这份程序一份」

用户拿到 1.6.10 的包，解压后的原话是：

> 「新发布的 zip 解压后，我的耗材里没有耗材，要导入后才看得到耗材。不要多版本公用一个耗材库，要独立。」

先说清楚**这不是 bug，是设计错了**。1.6.10 及以前，打包版的 `data_dir()` 候选顺序是
`%LOCALAPPDATA%\BambuPalette` → `%APPDATA%` → `%TEMP%` → 用户主目录，**exe 旁边的 `data\` 只在
写 `portable.txt` 时才排第一**。于是「解压一个新版本」和「换一份耗材档案」是两件被混在一起的事：
新版本一启动就去读**上一个版本写下的**那份档案，用户看到的是「我什么都没导入，这些耗材哪来的」。
打包脚本本身是干净的——`dist/BambuPalette-1.6.10-win64.zip` 共 212 个条目、56,964,568 字节，
里面没有 `data\`、没有 `filament-library.json`、没有 `presets\`、没有 `portable` 文件——
耗材**不是随包发的，是从 profile 里读来的**。

1.6.11 把两件事拆开：

| | 打包版（`is_frozen()`） | 从源码运行 |
| --- | --- | --- |
| 首选 | `exe 所在目录\data\` | `%LOCALAPPDATA%\BambuPalette\` |
| 退路 | `%LOCALAPPDATA%\BambuPalette-<副本名>\` → `%TEMP%\BambuPalette-<副本名>\` → `~\.bambupalette-<副本名>\` | 不带副本名（和以前一样，`portable.txt` 时 exe 旁边的 `data\` 排第一） |

* **退路也必须按副本分开。** 只把首选改成 exe 旁边是不够的：exe 目录写不进去时（Low 完整性标签、
  杀毒锁目录、只读介质）它会退到 profile，而 profile 正是原来那个共用位置——bug 会在最需要确定的
  场景里回来。所以退路目录名带 `<副本名>`：exe 所在文件夹名去掉程序自己的名字（`BambuPalette` /
  `FilamentColorStudio`），取前 40 个字符，末尾加 6 位摘要（`sha1(副本路径.casefold())[:6]`）。
  同一个文件夹名的两份副本靠摘要区分，读起来还是 `BambuPalette-1.6.11-win64-e773f6` 这种人看得懂的名字。
  去前缀这一步纯是为了不出现 `BambuPalette-BambuPalette-1.6.11`。
* **旧的共用档案不删、不自动接管，但也不难找。** `%LOCALAPPDATA%\BambuPalette\filament-library.json`
  是用户的耗材，直接接管就等于没改；删掉更不行。所以 `legacy_shared_library()` 只做一件事——
  在「这一份还没有档案」时告诉点「导入」的人该从哪个文件夹开始看（`_import_start_dir()`）。
  它也会看更早的 `%LOCALAPPDATA%\FilamentColorStudio\`，这样从最早那版升上来的人也只需点一下导入。
* **只有一种情况仍然自动改名接管**：`_adopt_legacy_data_dir()` 是对每一个候选目录逐个调用的，
  只有当这份程序**自己旁边真的写不进去**、轮到 profile 候选时，才会把 `FilamentColorStudio`
  改名搬进那一份自己的 `BambuPalette-<副本名>\`。现代那个 `BambuPalette\` 故意**不在**接管名单里。
* **第一次启动一定是空库。** exe 旁边的 `data\` 不存在 → 不在「已经有档案的目录」预扫里 →
  走「新建目录」分支 → `mkdir` + 写入探测通过 → 返回一个空目录。截图、自检、单元测试都靠
  `BAMBU_PALETTE_DATA_DIR` 覆盖（它仍然是整份候选列表），所以它们既不会看到真实耗材，
  也不会污染真实耗材。

代价写出来：用户从 1.6.10 升到 1.6.11，**「我的耗材」会变成空的**，要自己点一次「导入」
（对话框默认就开在旧档案那里）。这是用户明确要的行为，但它是这一版唯一需要用户动手的升级步骤，
所以 release notes 的「升级」一节必须把这个路径写全。

### 38.1 「抖动」为什么在透明图上点了没用（第 1 条）

老代码的判断只有两行，写在一个 `_sync_dither_state()` 里：只要图片上**任何一处** alpha 小于
`alpha_threshold`，就把「抖动」勾选框 `setEnabled(False)`，并把理由写进工具栏下面那行常驻说明
（「带透明区域的图片不能用抖动」）。理由是真的：带掩膜的图片在 `reduce_colours` 里会被**压缩成
一整行**再交给量化器——

```python
# 旧代码：有颜色的像素挤成一行，交给中位切分
source = Image.fromarray(rgb[keep].reshape(1, -1, 3), "RGB")
...
dither = Image.Dither.NONE
if keep is None and settings.dither:
    dither = Image.Dither.FLOYDSTEINBERG
```

Floyd–Steinberg 把量化误差推给**右边和下面**的邻居，而这一行上一半是假邻居；那一行上的扩散只是
噪点。所以程序选的做法是**拒绝**，而不是让你勾了发现什么都没变。

问题是「透明图」在插画里是常态（用户那张猪 262,144 个像素里有 **138,095** 个是透明的），一个
为了不出现噪点而整块关掉的选项，看起来就是「这个选项选不了」。

1.6.12 把它改成**能做对**：保留二维图形，只在图案范围里扩散。

| 函数 | 干什么 |
| --- | --- |
| `_inward_fill(rgb, keep, rounds=8)` | 把图案**往透明区域里长出去**：每轮让每个透明像素取它周围 3×3 不透明像素的平均色，长 8 轮；一直没长到的地方（大片背景的远端）统一填**图案自己的平均色**。 |
| `_dither_masked(rgb, keep, palette, pad=2)` | 裁到**图案外框 + 2 px**，填好，再用**已经定下来的调色板**（不是重新中位切分）做 Floyd–Steinberg，最后把掩膜外的像素写回 `-1`。 |

两处细节都踩过坑：

* **黑背景会渗进图案。** `image.convert("RGB")` 把透明变成**纯黑**，而误差扩散会把一个像素的错误
  推给右邻和下邻——旁边那块黑会顺着图案边缘渗进去。所以必须先填色：给邻居一个可信的颜色，再扩散。
  没长到的地方填**平均色**而不是黑：一整块同色区域自己扩散不出任何东西，而且掩膜最后会把它整块丢掉。
* **调色板表必须填满 256 项，而且多出来的项要重复真颜色。** `Image.quantize(palette=...)` 要求
  调色板图有 256 项，缺的部分如果是黑的，那就是一个图案里从没有过的颜色，量化器会乐意把深色像素
  分给它——**实测：4 色的调色板量化出 5 个类**（单元测试直接报
  `AssertionError: 5 not less than or equal to 4`）。所以多出来的项用真颜色**平铺**，算完再把
  索引 `mapped %= len(rows)` 折回真调色板。

同时删掉的东西和加上的东西一样重要：`_sync_dither_state()` 整个方法删掉（两个调用点一起），
说明文字里那句「带透明区域的图片不能用抖动」删掉。自检里对应的检查也跟着反过来：
**透明图上「抖动」必须是可勾的**（`page._dither.isEnabled()`），勾上以后
`page.result.indices[:, :8]` 全是 `-1`（透明条依旧不打印）、`:8` 之后全是有效类
（图案完整打印），而且**结果真的变了**（同一张图上开关抖动，分类不同的像素数 > 0）。

### 38.2 色块高亮只活了一帧（第 3、4 条）

`PictureView` 把「变淡的背景图」缓存起来，缓存的键里带着当前高亮的色块。老代码里那段是这样写的：

```python
def _dim_pixmap(self):
    if self._highlight is not None:
        return None      # 这一帧已经叠过高亮了，别再叠一次
    ...
```

本意是「别在高亮图上再叠一层高亮」，实际效果是**高亮只交给绘制方一次**：下一次任何重绘
（缩放、平移、点到别的软件再回来）拿到的都是 `None`，于是色块消失。用户看到的正是这个——
「预览放大和缩小的时候、在其他软件上点一下的时候，不继续显示色块」。

修法是把两件事分开：`_dim_pixmap()` 只负责**返回缓存的那张变淡图**，高亮由每次重绘时调的
`_build_highlight(result, selected)` 现叠。这样缓存图的键里也不再有 `_highlight`，缩放时不用重算。
自检里的检查是「两张连续 `grab()` 的图完全一样」加上「`zoom_by(1.25)` 之后
`page._dim_pixmap() is not None`」——两条都必须成立。

### 38.3 再点一次同一个颜色 = 取消（第 5 条）

这条看上去只是加一个信号，真正的坑在 Qt 的事件顺序：

**Qt 在自己的点击处理里，先移动 `currentRow`，再发 `itemPressed` / `itemClicked`。** 所以在
`itemPressed` 里记「现在选的是谁」已经晚了——记下来的会是被点中的那一行，于是「点了别的行」会被
判成「点了同一行」，刚点上去就取消掉。

所以 `ColourList` 给 `self._list.viewport()` 装了一个 `eventFilter`，在**按下事件被 Qt 处理之前**
记下 `_press_index`（鼠标底下那一行）和 `_press_shown`（那时预览里正在显示的色块）；真正的判断放在
`_on_row_clicked` 里：只有 `index == _press_index == _press_shown` 才发新的
`colourDeselected = Signal(int)`，多选模式下跳过（多选里再点一次本来就是「取消这一项」，
不需要退回上一张）。

`PicturePage` 这边多两个字段：`_shown`（现在显示的是哪个色块，没有就是 `-1`）和
`_preview_history`（看过的顺序）。`_select()` 在切换之前把**上一个** `_shown` 压进历史；
`_on_colour_deselected()` 弹出历史，退回上一个；历史空了就退回整张预览（`_shown = -1`）。
`_apply_edits()` 重建颜色行时把 `_shown` 复位成 `-1` 并清空历史——行已经不是原来那批了，退回一个
「上一批行里的第 3 个」是没有意义的。

自检里走的是**真鼠标点击**（`QTest.mouseClick(rows.viewport(), _Qt.MouseButton.LeftButton, pos=rect.center())`）：
点预览里的色块要能选中；点另一行色块要换过去；再点同一行要退回上一张；一路退到没有历史之后
`page._shown == -1` 且 `page._list.current() == -1`（列表本身也不再高亮任何一行）。

### 38.4 「这么多颜色，混不出来猪鼻子吗」（第 2 条）

这一条不能靠猜，先量。用户那张猪是 1024×1024，在「最大边长 512」下匹配，用**他真实的 41 卷库**：

* **不设上限**时程序自己要 **19 卷**（肤色 84.9%、橙色 6.4%、白色 6.3%、樱花粉 5.9%……）。
  其中猪鼻子那 `#DA4578` 的 **549 个像素（0.4%）**由「玫瑰红 84% + 红色 16%」打到
  **ΔE00 0.91**——也就是说混色引擎混得出来，是**上限**把它挤掉了。
* **上限 4（默认）**时，老代码的 `_fit_spool_budget` 是**按面积贪心**：最大的色块先挑料，挑到预算
  用完为止。脸占 85%，于是脸先拿走卷料，鼻子那 0.4% 只能退到「红色 + 肤色」之类的近似色上。
  把 4 卷的**全部 3,876 个子集**都评分（不只在贪心的那条路上）：贪心的加权平均 ΔE00 是
  **1.813**，最好的一套是 **1.249**——**贪心差了 31%**。
* 但「最好的」并不等于「最好看的」。把目标函数一个个换过去量：

| 目标函数 | 选出来的 4 卷 | 加权平均 | 最差块 | 鼻子那块 |
| --- | --- | --- | --- | --- |
| 加权平均优先 | 橙色 + 红色 + 肤色 + 黑色 | **1.458** | 10.02 | ΔE00 6.59（柔和粉红） |
| 最不像的块优先（minimax） | 同上 | 1.458 | 10.02 | 同上 |
| 超过阈值的误差优先 | 同上 | 1.458 | 10.02 | 同上 |
| 每块同等重要（不加权） | 同上 | 1.458 | 10.02 | 同上 |
| 平均 + 每块同等（0.25 混合） | 同上 | 1.458 | 10.02 | 同上 |
| **差块个数优先** | 玫瑰红 + 红色 + 肤色 + 青铜色 | 1.778 | **18.20** | **ΔE00 0.91 ✓** |

  前五种目标函数选出的是**同一组**。只有「差块个数优先」愿意为鼻子牺牲别处，代价是脸边上那块深棕
  （`#6C4531`，4,291 个像素）落到 ΔE00 18.20，渲染出来脸上有竖向色带——比鼻子偏色更显眼。
* 五卷会不会都好？也量了：**肤色 + 黑色 + 橙色 + 玫瑰红 + 红色**（加权平均 1.332）把鼻子、鼻孔、
  眉毛都画对，只剩眼睛偏橄榄色；六卷六色齐 1.539，反而更差。也就是说**四卷装不下这张脸**，
  而多要一卷并不是「更好」，是「换来换去」。

结论是：**「哪块重要」是审美，不是算法。** 程序能算的是「这一套料整体差多少」「有几块明显不对」，
算不出「猪鼻子必须像」。所以这一版**不替用户挑**，改成把候选摆出来让他自己选。

### 38.5 「耗材方案」面板：几套料，用户自己挑（第 2 条的落点）

`match_image()` 被拆成两半：

* `_prepare(source, palette, settings, progress)`：读图、缩放、`reduce_colours`（唯一贵的一步，
  41 卷 + 512 px 要约 1.7 秒）、合并近似色、给每个色块找最近的耗材条目；
* `_plan(prepared, max_spools, objective, progress=None)`：跑一次上限内的选料，再算每块的平均色，
  产出一个 `MatchResult`。

`match_image()` = `_prepare` + `_plan(cap, _budget_objective)`（**默认那套方案就是原来那个答案**，
所以「不选」和以前一模一样）。`match_options()` = `_prepare` 一次 + 对每个目标函数各跑一次 `_plan`，
卷集合相同的方案用 `frozenset` 合并掉。

界面上每一套写四个数字：**平均 ΔE00 · 最差 · 差块 · 用几卷**。其中「**差块**」= 色差 ΔE00
**超过 5** 的颜色有几个，它是这里最关键的一个数字：用户问的是「猪鼻子混不出来」，而「平均」回答
不了这个问题——平均最优那套的平均是 1.46，鼻子那块却是 6.59；小色块优先那套平均 1.78 更差，
鼻子那块却是 0.91。数字摆出来，选哪套就是用户自己的事了。

在 41 卷 + 上限 4 下，面板列两套（去重之后）：

| 方案 | 卷 | 平均 | 最差 | 差块 |
| --- | --- | --- | --- | --- |
| 总体最接近 | 肤色、红色、黑色、橙色 | 1.458 | 10.02 | 3 |
| 小色块优先 | 肤色、玫瑰红、青铜色、红色 | 1.778 | 18.20 | 1 |

选中的那一套会**跟着工程文件一起存下来**（`ProjectState.plan`，写进 `工程.json` 的 `plan` 键）。
打开工程时面板照原样列出它、**不重算**；1.6.11 及更早的工程没有这个键，读成空字符串并按「工程里
存的那一套」显示（可选键，格式没变）。

上限是**硬约束**：一开始还给过一套「多用 1 卷」（五卷那套，平均 1.603），用户随后明确要求
「耗材方案只能比等于小于耗材上线，不能大于耗材上线」，于是 `_PLAN_SPECS` 里的第四套和
`match_options(with_extra=...)` 形参一起删掉。用户对这台机器的交代是约束，不是建议：
方案宁可少给一套，也不越界。

### 38.6 选料：从贪心换成「上限内挑最好的一套」

`_fit_spool_budget` 现在这样工作：

1. 先按「每个色块需要哪几卷」建 `needs`（混色要两卷或三卷）。上限足够装下所有需要时**提前返回**
   （「这张图本来就装得下」），一点搜索都不做。
2. 卷按「需要它的色块面积」从大到小排队，只取前 `_BUDGET_ROLL_LIMIT = 22` 卷（尾巴上那些一卷只用
   一两个像素的卷不值得进搜索）。
3. 上限内**穷举**卷组合（`C(22, 4) = 7,315`，上限 `_BUDGET_SUBSET_LIMIT = 20_000` 个子集以内），
   每个组合算一次目标函数：能打印的色块取它到子集里最近色的 ΔE00，目标函数把这些值变成一个元组
   （元组按项比较，所以「差块个数优先」和「加权平均优先」共用同一套搜索）。
4. 组合太多时不硬穷举：按 `needs` 顺序**增量搭**一套，再逐个位置**试换**，换不动就停。
5. 预算小到连一个能打印的色块都没有时，退回 `_affordable_nearest()`（单卷里最接近的那一色）——
   宁可颜色差一点，也不给一个用不了的方案。

代价是匹配时间从 **1.7 秒到 2.0 秒**（41 卷、512 px、32 色、上限 4）：多出来的时间就是那几百个
子集的评分。

### 38.8 三条经验

1. **用户说「混不出来猪鼻子」时，别先动算法，先把「哪块不对」变成一个看得见的数字。**
   这一版真正的产出不是「更好的目标函数」（那是量了六种以后发现挑不出来的），而是
   **差块个数**这一个数字：它让用户自己在两套料之间一眼选出他要的那套。程序替他选，一定会选错
   一半人。
2. **上限是用户的约束，不是程序的建议。** 「多用 1 卷会更好看」这种方案看起来体贴，实际是把
   「我的机器只有 4 卷」这个前提丢掉了一次。要越界，应该由用户自己把上限改大——那是他的决定，
   写在设置里，看得见。
3. **源码全绿不等于打包版能跑。** 这一版的 exe 已经打包好、zip 都快发出去了，`--selftest` 才在
   冻结版里报 `ModuleNotFoundError: No module named 'PySide6.QtTest'`：`build/BambuPalette.spec`
   的 `EXCLUDES` 一直写着「这个程序用不到 QtTest」（那是把安装包从 250 MB 压到 90 MB 的手段），
   而这一版新加的自检用 `QTest.mouseClick` 点真控件，恰好是唯一需要它的地方。修法是从 `EXCLUDES`
   里拿掉 `PySide6.QtTest`，并把 `tools/verify_release_exe.py` 加成发版前最后一道闸门——它验证的
   是要发出去的那个文件，不是仓库里的源码。

### 39.1 「用到的耗材」并进「耗材方案」（第 1 条）

### 39.2 「选中的颜色」改成双击弹窗（第 2 条）

`colourDetailDialog`、最小宽度 380、里面是一个无边框滚动区装 `self._detail`、一个「关闭」按钮），
`_on_colour_activated()`（列表行被双击时发）负责 `show()/raise_()/activateWindow()`，标题写成

### 39.3 方案更多 + 筛选（第 3 条）

「更多组」不是把目标函数编出花来，而是**同一个目标函数下的不同搭法**：`_PLAN_SPECS` 从四元组变成
五元组，最后一项是 `variants`（总体最接近 3 组、最不像的色块优先 2 组、小色块优先 2 组），
`_plans(..., limit=variants)` 返回前 K 个不同卷集合，`_offer_options()` 再用
`frozenset(rolls)` 去重。备选行的标题写「总体最接近（备选 1）」，说明里加一句「同一目标下的另一种
搭法。」——用户看得到它是同一个理由下的第二种选择，而不是另一种口径。

筛选是**两个集合**：`require`（必须包含）与 `avoid`（不要用），从 `match_options()` /
`rematch_options()` 一路传到 `_budget_fits()`：

1. `_with_required()`：对每个缺的「必须有」卷，在现有色块里找**换过来最划算**的那一块（代价 =
   `counts × ΔE00(这块的色, 离它最近的含该卷条目)`），把这块的条目换成含该卷的最近色。块的边界和
   像素分布一个都不动。
2. `_without_banned()`：配方里含禁用卷的块，换成 `_nearest_free()`——不含任何禁用卷的最近色。
3. `_budget_fits(..., require=, avoid=)`：候选卷组合先过 `require - spent or (avoid & spent)`，
   **不合格的组合不进候选**，所以「宁可少列一套，也不给一套违规的」。
4. 连「图本来就装得下」那条提前返回也要过筛选（`require <= untouched and not (avoid & untouched)`）。

界面在 `app/ui/plan_filter.py`：一行一个耗材、**一行三态**（不要求 → 必须有 → 不要用），状态同时用
三种方式表达（前缀「必须有 · 」、粗体、不要用还加删除线），「全部不要求」一键清空；如果「必须有」
的卷数已经超过「耗材上限」，对话框当场写清楚「不会有搭配能满足——先改上限，或者少要求几卷」，
不让用户等一次必然失败的匹配。

**这一版踩到的坑**：`_on_rematch()` 忘了把 `require/avoid` 传给 `match_options()`，于是「重新匹配」
会把筛选悄悄丢掉——自检抓到的是「第三套方案没含『必须有』的那一卷」（前三套方案里只有两套含它）。
修完之后，空结果时的话也分成两句：有筛选时说「按现在的筛选条件没有找到能用的耗材搭配，先放宽筛选
或者提高耗材上限。」，没筛选时还是原来那句。

### 39.4 「按当前色块重新匹配」（第 4 条）

这是四条里唯一需要动核心的一条。`rematch_options(result, palette, settings, *, pinned, require,
avoid, progress)` 的做法是：**把现在每个色块的「图片颜色」当成新的目标**，而不是重新读图片。

* 目标色 = `result.region_colour(index)`（删除的块不在 `result` 里，所以**不可能回来**；合并过的块
  只剩目标块的颜色，所以「按色块 b 的来匹配」是天然的）。
* 这些目标色送进 `_nearest_entries()` 找最近条目，构造
  `_Prepared(image=None, counts=result.counts, indices=result.indices.copy(), pictures=targets)`
  ——`pictures` 就是 1.6.12 里加的那个字段：`_region_means()` 有它就按 `fit.sources` 取**胜者块**的
  图片颜色，没它才回头去算图片均值。`_renumber_sources()` 返回的第四项 `sources`（「这个结果色来自
  原来的哪一块」）就是为这件事留的：合并进来的颜色用的是胜者的颜色，不是几块的加权平均。
* 手改过的块（`_replaced`）走 `pinned` 覆盖。注意 `_replaced` 的键是**基准结果的下标**、而这里要的是
  **当前色块的下标**，所以要先经 `_live_map` 翻译一次，否则改过颜色的块会在重匹配后跳回自动答案。
* 两块最终落到同一卷上时会**合成一块**（同一卷不会在两块里重复出现）。自检因此把「色块数不变」
  改成两条更准的：**不会变多**、**同一卷不在两块里重复**；「删掉的色块没回来」用的是更硬的证据——
  `total_pixels - printed_pixels`（不打印的像素数）必须和删除后完全一样。

第 8 条后面还跟着一句更要紧的观察，它其实是第 8 条的反面——不是文本放哪儿，而是**那一行到底有没有

配的截图里，「最不像的色块优先」那一行写着 **平均 ΔE00 21.80 · 最差 22.45**，而同一屏的
「总体最接近」只有 **1.52 · 9.65**——被指为「优先」的那一行，数字比谁都不像。

### 40.1 行上的数字，必须就是这一行自己印出来的色差

这是七条里唯一动了算法的一条，也是这一版真正的 bug。

**病灶**：`_budget_fits()` 里那个打分函数用的是**替代色的色差**——候选卷集合里被拒绝的颜色，
取它到「最近的能印的替代色」的距离（`worst[surplus] = columns[surplus].min(axis=1)`），再把每块
的像素当权重平均。而屏幕上那一行数字来自 `match_fidelity_report(result)`，它量的是完全另一件事：
**折进这一块的所有像素混出来的颜色** vs 这一块最终印的颜色。两者在「一块用一个条目」时相等，一旦
一块吃掉了几种颜色就不相等——于是**排序用的数和显示的数不是同一个量**，行上写「最差 22.45」的那一行
照样能排在最前面。同一处还有一个 `if len(printable) == len(pool): return (0.0, 0.0)` 的提前返回：
颜色数没超上限时它直接宣称零误差，而报告里那一套明明是 0.90。

**修法**：让打分函数和报告用同一把尺。`_budget_fits(..., region_rgb=, blend_regions=)` 里的
`_score()` 现在按 `ranks` 与 `nearest = _table()[:, printable].argmin(axis=1)` 把每一块吃掉的像素
**折进这一块**：

```python
blend[rank] += weights[position] * region_rgb[position]
means = np.rint(blend / np.maximum(pixels, 1.0)[:, None]).astype(np.uint8)
values = np.atleast_1d(_color.delta_e_2000(
    _color.lab_from_rgb(means),
    np.asarray([labs[position] for position in printable], dtype=np.float64),
)).astype(np.float64)
return objective(values, pixels / pixels.sum()), printable
```

* `region_rgb` 由新的 `_pool_region_means(prepared)` 提供：`pictures` 有就直接用（「按当前色块重新
  匹配」那条路），否则把原图像素按 `prepared.indices` 分组求和 ÷ `np.maximum(prepared.counts, 1)`；
* `blend_regions=False` 时不折（改用 `np.asarray([region_rgb[position] for position in printable])`）：
  「按当前色块重新匹配」要求**合并过的块保留胜者的原色**（1.6.13 第 4 条那条澄清），折一下就把
  用户改过的颜色又揉平了；
* `region_rgb is None` 时保留旧代理打分，供老调用方 `_fit_spool_budget()` 继续用；
* 提前返回那个 `(0.0, 0.0)` 删掉了——「数不出差别」和「没有差别」不是一回事。

**实测**（240×180 的合成猪脸图 + 5 卷料 白 `#F2F0EB` / 橙 `#F08A24` / 肤色 `#FAD4B7` /
玫瑰红 `#E0567A` / 杏色 `#E8C39E`，颜色数量 8、耗材上限 3）：
三个目标函数各自的冠军，在**全部 18 个候选**里就是各自那一项的最小值：

| 目标函数 | 冠军的 ΔE00 平均 | 冠军的最差 | 冠军的差块 | 那一套用的卷 |
| --- | --- | --- | --- | --- |
| `_objective_closest` | **2.66**（最小） | 8.86 | 1 | 玫瑰红 + 白 + 肤色 |
| `_objective_worst` | 4.31 | **4.68**（最小） | 0 | 橙 + 白 + 肤色 |
| `_objective_distinct` | 4.31 | 4.68 | **0**（最小） | 橙 + 白 + 肤色 |

（注意上面两行是同一套卷：同一个卷集合可能是几个口径共同的冠军，而面板按卷集合去重、只列一次，
所以它会顶着**先认领它的那个口径**的名字出现——名字只说明它是按什么标准挑出来的，选的是卷。）
回归测试 `test_each_criterion_wins_the_number_it_is_named_after` 把这条性质钉住了：对每个口径取
`_plans(..., limit=6)` 的**全部**候选，逐项断言「差块 ≥ distinct 冠军的差块」「最差 ≥ worst 冠军的
最差 − 1e-6」「平均 ≥ closest 冠军的平均 − 1e-6」。

**踩到的坑**：`app/spectral/color.py:567` 的 `delta_e_2000()` 在两边各只有一行时**返回裸 float**，
不是数组——`_score()` 对只有一个候选色块的图（单元测试里那四条「上限 1」的用例）当场炸出

```
ValueError: matmul: Input operand 1 does not have enough dimensions (has 0, gufunc core with
signature (n?,k),(k,m?)->(n?,m?) requires 1)
```

包一层 `np.atleast_1d()`（`lab_from_rgb` / `delta_e_2000` 本身都支持 (N,3) 批量）即好。

### 40.4 「这个模型需要的颜色」→「打印图片需要的颜色」，面板能一路往上拖（第 2、3 条）

面板标题改成「打印图片需要的颜色」（`app/core/project.py:18`、`:228` 的说明文字同步改）。前半句是
措辞，后半句是真 bug：那块面板以前被内容的最小高度**顶住**——「用到的耗材」清单的滚动区带着
`setMinimumHeight(58)`，于是分隔条再怎么往上拖也只能拖到那儿。

改法是把整个方案面板包进 `self._plan_scroll = _scrollable(self._plan_box)`，并给它
`setSizePolicy(Preferred, Ignored)` + `setMinimumHeight(48)`：**内容不再决定面板的最小高度**，滚动
交给这一层。分隔条于是可以自由上滑，也能整块收起（`right.setCollapsible(0, True)`；下面那块颜色
清单仍然 `False`，不允许被拖没）。自检里量出来的最小高度是 **92 px**（标题 + 48 的正文），不是
拍脑袋的 60——所以那条检查的阈值写成 `<= 100`，并附一句实测值。

### 40.5 「关于」变成「帮助」：把说明从图上搬进窗口（第 5、6 条）

新建 `app/ui/help.py`：`HelpDialog(text, parent)` —— 非模态 `QDialog`，objectName `helpDialog`，
标题「帮助」，里面是一个无边框 `QScrollArea` 装可选中的正文 `QLabel`（objectName `helpBody`），
底部「关闭」。`MainWindow` 的 `_about_button`（「关于」）换成 `_help_button`（「帮助」），
`_help_text()` 把三段拼起来：

```
图像转换这一步：…（原来的四行常驻说明，PAGE_HELP）
「耗材方案」这几行：…（plan_help()）
算法与版本：…（_about_text()，内容和以前一样）
```

图片页那边 `PAGE_HINT` 改名 `PAGE_HELP`、常驻标签与 `layout.addWidget(self._page_hint)` 都删掉，
只留 `help_text()` 供主窗口取用——**同一段文字只有一个出处**，自检也改成断言
`page.help_text() in window._help_text()`（原来那句「提示行 == 这一套的说明」变成「面板上没有说明、
帮助里有」）。

### 40.6 匹配完不再默认选中第一个颜色（第 7 条）

`_apply_edits()` 里原来有一句 `if target < 0 and len(result.palette): target = 0`：编辑后找不到原来
那一块时，**退而选中第 0 块**。于是「选耗材方案」这件事看着像「帮你选了第一个颜色」。删掉这个兜底
（`0 <= target < len(result.palette)` 才 `_select(target)`，否则 `_show_colour(-1)` 把列表高亮和详情
一起清掉），并在 `_adopt_options()` 落新结果之前先 `self._list.clear_selection()`：新匹配从「什么都
没选」开始，而**编辑仍然跟着你点过的那一块走**（`_apply_edits(keep=...)` 的语义没变）。没有选中时
「删除」「更换颜色」自然是灰的。

### 40.8 三条经验

1. **「显示的数」和「排序用的数」必须同源。** 这一版的 bug 不是算错了，是**算了两个不同的量**：
   排序用代理色差、显示用真实混色色差，两者只在一块一条目时重合。修法不是调代理的权重，而是让
   排序函数直接调用报告那把尺（连「折进这一块」的像素加权都照搬）。用户看到的矛盾数字
   （21.80 / 22.45 排在 1.52 / 9.65 前面）就是这两个量分家的指纹。
2. **删掉一个会自动发生的事情，要在最靠近它的地方删。** 「不要默认选中第一个颜色」看起来是界面
   策略，实际源头是 `_apply_edits()` 里对一个找不到的锚点的兜底。把兜底删掉、再在落新结果前清一次
   选择，行为就对了——而不是在下游补一句「如果是新结果就取消选中」。
3. **改界面之后，先跑一遍检查脚本，再谈别的。** 这一版第一轮红灯几乎全来自检查脚本：
   `page._page_hint` 已经不存在（`AttributeError`）、面板标题改了、提示行不再等于 `option.note`、
   `_panel_titles()` 走 `_plan_box.parentWidget()` 撞上新的 `QScrollArea`。自检和 smoke 在这一版里的
   价值，主要就是逼着「界面挪窝」这件事在交付前被看见一次。
